## 1. 角色、窗口与设备

| 角色 | 账号 | 用途 |
|---|---|---|
| 员工 | `demo` | 跑任务、冻结外发、改收件人/附件、看回放 |
| 设备助手 | `helper` | 设备页点「确认」把挑战帧下发到 A，经 SLE 转给 B，等待物理按键 |

- 密码在 `prototype/data/initial-users.txt`，只在本机看，**不要出现在画面里**。
- 四眼原则：`demo` 发起的操作不能由 `demo` 自己批准，必须用 `helper`。
- **两个账号必须用两个独立浏览器会话**：普通窗口登录 `demo`，无痕窗口（Ctrl+Shift+N）登录 `helper`。同一浏览器两个普通窗口共用 Cookie，后登录的会覆盖前一个，两个窗口都会变成同一角色。
- B 板 = 确认板（`SAFE_OFFICE_DEVICE=ws63-B`）；A 板 = 执行板（`SAFE_OFFICE_ACTUATOR_DEVICE=ws63-A`）。
- 同屏镜头：显示器 + B 板 OLED 在一个画面里；手机/相机用三脚架固定，先对焦 OLED。

## 2. 录制前检查（建议提前 30 分钟）

### 2.1 插板与识别端口

1. 两块板都插 USB（数据线，不是只供电线），确认设备管理器出现两个 `USB-SERIAL CH340`。
2. 逐块识别身份（每次插拔后都要重做）：

```bash
cd prototype
node scripts/ping-device.cjs --port COM11 --device ws63-A   # A 板直连
node scripts/ping-device.cjs --port COM12 --device ws63-B   # B 板直连（仅识别用）
node scripts/ping-device.cjs --port COM11 --device ws63-B   # 关键：A 经 SLE 转发到 B
```

三条都通过才算双板链路正常。把实际端口记下来；如果返回失败，换端口再试，**不要凭上次的 COM 号猜**。

3. 关闭所有占用串口的程序：HiSpark Studio 串口监视、PuTTY、其他 `npm start`、`serial-cli`。同一串口只能被一个进程打开。

### 2.2 修正端口配置

本项目用 **M3' 双板中继**拓扑，不是 PC 直连 B：

- PC 只连 **A（执行板）** 的 USB；挑战帧发到 A，A 经 SLE 转给 **B（确认板）**，B 按键后决定原路返回。
- `SAFE_OFFICE_NEARFIELD_PORT` = **A 的端口**（例：`COM11`）
- `SAFE_OFFICE_ACTUATOR_PORT` = **A 的端口**（同一块板执行 IO12，例：`COM11`）
- `SAFE_OFFICE_DEVICE=ws63-B`（确认钥匙在 B）
- `SAFE_OFFICE_ACTUATOR_DEVICE=ws63-A`（执行钥匙在 A）
- B 的 USB 只供电，PC 不打开 B 的串口；`COM12` 只是识别/烧录时用。

只有 A 板不可用时，才退回“PC 直连 B”：`NEARFIELD_PORT=COM12`。这种情况下没有 SLE 中继，视频里不要讲双板链路。

> 2026-11-27 现场：A 板原固件是厂商 Demo，已重烧 exec 固件并重新配网；两块板 PONG 均通过，`ping --port COM11 --device ws63-B` 经 SLE 转发也通过。

### 2.3 启动服务（录制用：强制模拟邮件）

本机 `config.env` 配了真实 QQ SMTP。录制外发时如果走真实 SMTP，会真的尝试发信、结果不可控。用下面的命令启动，空环境变量优先于配置文件，强制 FakeMailer：

```bash
cd prototype
SAFE_OFFICE_SMTP_HOST= SAFE_OFFICE_SMTP_ACCOUNTS= SAFE_OFFICE_SMTP_USER= \
SAFE_OFFICE_SMTP_PASS= SAFE_OFFICE_IMAP_HOST= npm start
```

启动日志应出现：

- `执行端：ws63-A @ COM11 / IO12 继电器`
- 挑战路径：PC → A(COM11) → SLE → B(COM12)；B 的 USB 只供电
- 邮件为模拟发送（无 SMTP 账号）
- 挑战有效期：`SAFE_OFFICE_CHALLENGE_TTL_SEC=90`（已写入 config.env；默认 30 秒太短，换内容来不及）

### 2.4 模型选择（二选一，先拍板）

**已拍板：全部镜头用真实模型（DeepSeek `deepseek-flash`）**，不隐藏顶栏。

| 项 | 说明 |
|---|---|
| 启动 | 保持 `config.env` 的 DeepSeek 配置，只清空 SMTP/IMAP 环境变量（见 §2.3） |
| 注入样例 | 用新样例「攻击：外部材料注入（云侧）」，约 8–15 秒；实际结果是 M3 隔离 + 闸2拒绝，不写“计划校验移除动作” |
| Mock | 不用于录制，只保留离线复现 |

### 2.5 准备附件与窗口

1. 桌面准备两个文件，**同名同大小、内容不同**：
   - `agenda.txt`：`Agenda: initial draft`（21B）
   - `agenda.txt`：`Agenda: updated draft`（21B）
2. 浏览器开两个**独立会话**：普通窗口登录 `demo`（员工），无痕窗口登录 `helper`（设备助手）；缩放 110%，隐藏书签栏。
3. 预先打开页面：工作台、命令台、设备、回放。
4. 关闭微信/QQ/系统通知，开启专注助手；录屏软件只录浏览器窗口，避免露出其他资料。
5. 试录 10 秒：确认麦克风、OLED 字迹、网页小字都能看清。

## 5. 按键口径与重录点

| 项 | 口径 |
|---|---|
| 批准 | 短按 KEY2，<600ms；**轻点立即松手** |
| 取消 | 长按 KEY2，≥600ms |
| 等待 | OLED 摘要出现后停 2 秒再按，给镜头对焦时间 |
| 旧挑战 | 先让助手点「确认」把旧帧发到板上，再改网页内容，最后按旧键 |
| 新挑战 | 旧挑战作废后重新发起；一个时间只允许一个 pending |
| TTL | 挑战 90 秒；助手点「确认」后串口等待约 65 秒，改动要在窗口内完成 |
| 误长按 | 板端会回取消；本段重录，不要剪成“批准” |

**常见失败**：

1. 板子没插/端口变了 → 重跑 `ping-device`，改 config.env，重启服务。
2. 串口被占用 → 关掉串口监视/旧服务，必要时拔插 USB。
3. 助手页没有新挑战 → 设备页不会自动刷新，点一次「设备」导航或刷新页面。
4. 板端显示旧摘要但 PC 报超时 → 按键太晚（>65 秒）或帧没下发；重做本段。
5. 执行显示失败 → 检查是否误走了真实 SMTP；确认启动命令里的空环境变量生效。
6. 误触「发起挑战」而非「确认」→ 设备页的「发起挑战」只创建挑战，真正下发是 OLED 面板里的「确认」。
7. 两个窗口登录后都变成同一角色 → 同一浏览器共用 Cookie；必须普通窗口 + 无痕窗口分别登录。
8. 找不到「修改收件人与附件」→ 只有**外发且冻结/已执行**的操作才有；在「审批」页点「详情」，详情显示在列表下方，不是弹窗。
