# WS63 确认适配器（v0.11）

更新：2026-10-18。范围：Node 侧软件适配器 + 虚拟确认端；**未接**串口/SLE、真实按键/OLED、真实邮件。板端状态机仍以 `ws63/protocol.c` 为准。

> 目标：把已有的 SFC1 二进制协议（CHALLENGE/DECISION）真正接到 v0.10 的"冻结操作 → 确认 → 发送"闭环，让无硬件时也能跑通正常/取消/超时/重放/篡改/错设备；上板时只替换传输层。

---

## 1. 组件

| 文件 | 职责 |
|---|---|
| `prototype/src/nearfield-confirm.cjs` | A 端 `NearfieldConfirmer` + B 端 `VirtualDevice` + 环回传输 + `confirmWithFulfillment` |
| `prototype/test/nearfield-confirm.test.cjs` | 14 项测试（状态机/帧/窗口/闭环） |
| `prototype/demo-nearfield.cjs` | 6 幕演示（`npm run demo:nearfield`） |

```
冻结操作（operation.cjs / SQLite）
        │  operationHash（32B）、protocolAction、taskId、expiresAt
        ▼
NearfieldConfirmer（A 端）── CHALLENGE ──> transport ──> VirtualDevice（B 端）
        │  nonce/过期/重放窗口                                │  展示摘要
        │  MAC/设备/操作绑定                                   │  按键：确认/取消
        ◀────────────── DECISION ─────────────────────────────┘
        │
        ▼
FulfillmentService.confirm(operationId, { confirmedHash, deviceId, confirmationId })
        │
        ▼
FulfillmentService.send(outboxId) → FakeMailer
```

- `transport` 契约只有 `async send(frame: Buffer) -> Buffer | null`；`null`/抛错表示确认端无有效应答。
- `VirtualDevice` **不是硬件**：它用真实 HMAC-SHA256 签决定，但密钥在 Node 堆内存，设备身份只是一个 8 字节标识。

## 2. 字段映射

| SFC1 字段 | 来源 | 说明 |
|---|---|---|
| `task_id` (8B) | `deriveTaskId(operation.taskId)` | 字符串经域分隔 SHA-256 取前 8B；`Buffer(8)` 直通；C 端不参与派生，B 原样回显 |
| `nonce` (16B) | `crypto.randomBytes(16)` | 一次性；可用 `randomBytes` 注入做确定性测试 |
| `action` (1B) | `operation.protocolAction` | 1 外发 / 2 删除 / 3 打印 / 4 设备控制 |
| `target_hash` (32B) | **`Buffer.from(operation.operationHash,'hex')`** | 直接使用冻结记录的 32 字节哈希，**不重新哈希 JSON**（遵守 docs/08 契约） |
| `issued_at` / `expires_at` | A 端秒级时钟 | `expires_at = min(now + ttlSec, floor(operation.expiresAt/1000))`；`now >= expires_at` 即过期 |
| `summary` (≤96B) | `buildSummary(operation)` | `<动作标签>｜<subject>｜→ <recipient>`；控制字符换空格，按 UTF-8 字节截断，剩余 ≥3B 才补 `…` |
| `decision` | B 端按键 | 1 确认 / 0 取消 |
| `device_id` (8B) | B 端配置 | A 端只与**可信配对配置**中的 `expectedDeviceId` 比较，不用应答里的字段作为期望值 |
| `decided_at` | B 端秒级时钟 | 仅记录/展示；A 端用自身时钟判过期，不比较两端时钟 |

`confirmationId` 写入操作记录，格式：`ws63-<taskIdHex>-<nonceHex>`；`deviceId` 写入 `deviceLabel`（可信配置标签）。

## 3. 校验顺序（A 端）

组合了 C 的 `proto_decode_decision` + `proto_accept_bound_decision`：

1. 帧头/长度/版本/类型、**MAC**、`decision` 值域（`decodeFrame` 先做，MAC 先于绑定）。
2. 无 pending → `STATE`。
3. `task_id` 不符 → `TASK`。
4. `nonce` 不符 → `NONCE`。
5. nonce 已在 8 条已用窗口 → `REPLAY`。
6. `now >= expires_at` → 标记已用 + 清空 + `EXPIRED`。
7. `decision > 1` → `DECISION`（解码已拦，防御性保留）。
8. 设备 ID 与可信配置不符 → `DEVICE`。
9. 最终冻结记录复核（`verifyOperation` + `state==='frozen'` + 动作/哈希一致）→ `OPERATION`。
10. `decision === 0`（取消）→ 标记已用 + 清空 + `DECISION`（`cancelled:true`）。
11. 成功 → 标记已用 + 清空 + 返回批准结果。

> 与 C 的差异：C 的 `accept_decision_internal` 在函数内部先查状态再复核 MAC，但其部署路径也是"先 `proto_decode_decision` 再 `accept`"，因此有效顺序与上表一致。C 的 `REPLAY` 分支基本是防御性代码（pending 清空后先返回 `STATE`）；正常"成功后重放"在 Node/C 都返回 `STATE`，本项目测试按实际行为断言。Node 额外预检版本/类型，所以能区分 `VERSION`/`TYPE`；`TIMEOUT` 是 Node 本地传输结果，对应 C 侧等待到过期（`EXPIRED`）的路径，nonce 同样被消费。

### nonce 消费语义

| 结果 | pending 清空 | nonce 进入已用窗口 |
|---|---|---|
| 成功 | ✅ | ✅ |
| `DECISION`（取消） | ✅ | ✅ |
| `EXPIRED` | ✅ | ✅ |
| `TIMEOUT`（无应答/传输错误） | ✅ | ✅ |
| `STATE` / `TASK` / `NONCE` / `REPLAY` | ❌ | ❌ |
| `FRAME` / `VERSION` / `TYPE` / `MAC` | ❌ | ❌ |
| `DEVICE` / `OPERATION` | ❌ | ❌ |

- 已用窗口是 **8 条 FIFO**，仅存 RAM，重启丢失（与 C 的 `PROTO_REPLAY_WINDOW` 一致）。
- 未过期 pending 不能被新挑战覆盖（`STATE`）；过期 pending 先消费其 nonce 再让位。
- `MAC/DEVICE/OPERATION` 失败后 pending 仍有效，可用同一 pending 重试；`requestApproval` 不会自动取消。

## 4. 集成方式

```js
const { confirmWithFulfillment } = require('./src/nearfield-confirm.cjs');

const { approval, operation, outbox } = await confirmWithFulfillment({
  fulfillment,                       // FulfillmentService
  confirmer,                         // NearfieldConfirmer（注入 transport）
  operation: store.getOperation(id), // 冻结记录
});
await fulfillment.send(outbox.outboxId);
```

也可以直接使用状态机：

```js
const { pending, frame } = confirmer.beginChallenge(operation);
const reply = await transport.send(frame);          // 真实链路在这里换掉
const approval = confirmer.acceptDecision(pending, reply, { finalOperation: operation });
```

- `beginChallenge` 先用 `verifyOperation` 复核冻结记录；`acceptDecision` 再复核最终记录，任何正文/收件人/附件/字段变化都拒绝。
- 取消/超时**不自动**改操作状态；调用方可显式 `store.setOperationState(id, 'rejected')`。
- 适配器绑定的是调用方传入的冻结记录快照；`fulfillment.confirm` 会再读库中当前记录并重算，任一变化拒绝（不是原子事务，但有两道校验）。
- 审批成功但 `fulfillment.confirm` 时操作刚好过期/记录变化 → `confirm` 抛错，而 nonce 已消费；必须新建操作，不能复用同一挑战。
- `FulfillmentService.confirm` 的 API 未改动；适配器只是"可信调用方"。

## 5. 演示（6 幕）

```bash
cd prototype
npm run demo:nearfield
```

1. **正常**：挑战 → 设备确认 → 记录 confirmed → 发送 sent；
2. **取消**：`DECISION`，nonce 消费，操作仍 frozen，调用方显式标 rejected；
3. **不在场/超时**：`TIMEOUT`，新 nonce 可重试；
4. **重放**：旧 DECISION → `STATE`；复用 nonce → `REPLAY`；
5. **篡改与记录变化**：改决定帧 → `MAC`；改冻结记录 → `OPERATION`（失败不消费 pending）；
6. **错设备**：错密钥签名 → `MAC`；同 key 错设备 ID → `DEVICE`。

## 7. 边界

- **虚拟设备不是硬件**：没有 SLE/串口；`VirtualDevice` 只是协议对端替身。
- **密钥在 Node 堆内存**：预共享 32B 密钥，能读进程就能读密钥；不是 HUKS/TEE。
- **只覆盖冻结操作闭环**：`runtime.cjs` 的闸4 仍使用 `ConfirmationService` 进程内模拟确认，不能据此声称"运行时已接 WS63"。
- **确认 API 仍是进程内可信调用**：`FulfillmentService.confirm` 可以被调用方绕过适配器直接交哈希；适配器证明的是"谁对哪个哈希按了确认"，不是调用路径安全。
- **不证明距离/本人身份/防中继**：SLE 连通、按键、8 字节设备 ID 都不构成这些保证。
- ~~**窗口不持久化**~~：✅ 2026-11-04 已解决（M1）——nonce 窗口落板端 NV（`sfc1_nv.c/h`），断电重上电后旧帧仍 `REPLAY`。

### 串口真板接入用法（2026-11-04）

```bash
# 控制台启动时带上串口（不设置则继续用虚拟设备）
SAFE_OFFICE_NEARFIELD_PORT=COM11 npm start

# 不启动 Web，直接用服务层冒烟
npm run console:serial -- --port COM11 --demo-key
```

行为差异：挑战帧发到板子后，**决定来自物理按键**（短按批准 / 长按取消），
`decideChallenge` 的 `decision` 参数只参与四眼原则等权限校验，不再决定结果；
串口打不开时返回 `code:"TRANSPORT"`，操作保持 `frozen`、零发送。

`/api/bootstrap` 与 `/api/state` 会带 `nearfieldSerial: true`，审批页顶部因此显示
"已接真板（串口）：请在板端按键确认"的提示——页面上的批准/取消按钮只负责**发起挑战**。
