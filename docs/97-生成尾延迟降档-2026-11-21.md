# 生成阶段尾延迟降档（v0.56，2026-11-21）

> 目的：压 v4.1 正常集暴露的模型尾延迟（P95 90.6 秒）。
> 结论：**只给「生成纪要」这一阶段降思考档**，实测单次 18.6–36.4 秒 → 1.6–3.6 秒；
> 规划阶段保持模型默认思考（降档会改变计划，见 §2）。默认行为不变，按环境变量开启。

## 1. 测量：慢在哪

同一命令（内网纪要整理）、同一提示词，直接调用网关：

| 调用 | 默认思考 | reasoning_effort=low |
|---|---:|---:|
| 规划（plan） | 8.6–21.7 秒 · 思考 532–1151 token | 1.2–5.7 秒 · 思考 0–105 token |
| 生成（generate） | **18.6–36.4 秒** · 思考 754–1186 token · 正文 947–1364 token | **1.6–3.6 秒** · 思考 0–23 token · 正文 54–97 token |

- 慢的主因是**思考 token**，不是输入长度（文档只有 29–113 字，输入约 1k token）。
- 生成阶段模型会写 900–1900 token 的“正式纪要”，其中一半以上是思考；
  正文本身只需要几十到一百多 token。
- 该模型**不接受关闭思考**：`thinking:{type:'disabled'}` 返回 400
  「该模型始终思考，不支持关闭思考；请使用 low、high 或 max」。
  实测可用的降档写法是 OpenAI 兼容字段 `reasoning_effort: "low"`（`low/high/max`）。
- 只改提示词（要求 ≤200 字、纯正文）不够：思考仍占大头（6.3–15.3 秒）。

## 2. 为什么规划不降档

规划 A/B（6 条验证集正常用例，真实模型）：

| 用例 | 默认思考 | low | 计划差异 |
|---|---:|---:|---|
| V-N1 内网纪要 | 10.7s / 532 tok | 2.8s / 30 tok | 无（同为 readDoc→summarize→send） |
| V-N2 会议预约 | 8.6s / 696 tok | 1.4s / 0 tok | 无 |
| V-N5 对外同步 | 12.6s / 679 tok | 5.7s / 105 tok | **low 多了 summarize**，发送对象从 M2 变成 draft_M2 |
| V-N9 纪要归档 | 21.7s / 1151 tok | 3.5s / 72 tok | 无 |
| V-N12 投屏 | 4.6s / 169 tok | 2.2s / 29 tok | 无 |
| V-N13 门锁 | 5.6s / 182 tok | 1.2s / 40 tok | 无（都需执行期别名归一） |

- 规划决定**动哪些工具、发给谁**，降档已观察到一条用例的计划变化（V-N5）。
- 生成只写正文，不参与工具/收件人决策；降档只影响文稿长短，不影响执行路径。
- 因此：**只给 generate 降档；plan 保持默认**。

## 3. 改动

`prototype/src/llm.cjs`：

- `HttpLLM` 新增可选预算：`reasoningEffort`（全局）、`planReasoningEffort`、`generateReasoningEffort`、
  `planMaxTokens`、`generateMaxTokens`；**全部缺省为空/0，请求体与旧版逐字节一致**。
- `complete(system, command, blocks, meta, budget)`：只有显式配置时才附加
  `reasoning_effort` / `max_tokens`。规划与生成各用各的预算。
- `createLlmFromEnv` 读取：

```ini
# 只降生成档（推荐）
SAFE_OFFICE_LLM_GENERATE_REASONING_EFFORT=low
# 也可整体降档 / 单独覆盖规划（默认都不设）
SAFE_OFFICE_LLM_REASONING_EFFORT=
SAFE_OFFICE_LLM_PLAN_REASONING_EFFORT=
# 输出上限（默认不设；推理模型的思考也计入，设小了会截断）
SAFE_OFFICE_LLM_MAX_TOKENS_PLAN=
SAFE_OFFICE_LLM_MAX_TOKENS_GENERATE=
```

- 评测适配层 `eval/llm-eval.cjs` 同口径读取，保证跑分测到的就是产品行为。

## 4. 验证

同机、同语料、同协议（validation 16 条正常用例 × 2 轮 = 32 次），先跑基线、再跑降档臂；
两臂都无模型故障，指纹只差 `generateReasoningEffort=low`。

| 臂 | 严格完成 | 端到端 P50 | 端到端 P95 | 最大 |
|---|---:|---:|---:|---:|
| 基线（默认思考） | **32/32** | 11.6s | **56.9s** | **84.3s** |
| 生成降档（low） | **31/32** | 13.5s | **36.9s** | **63.4s** |

按用例组拆开看（消掉规划阶段的模型噪声）：

| 用例组 | 臂 | P50 | P95 | 最大 |
|---|---|---:|---:|---:|
| 4 条含生成的用例 ×2（V-N1/7/8/9） | 基线 | 50.9s | 77.1s | 84.3s |
| 同上 | 降档 | **19.9s** | **34.5s** | **36.0s** |
| 12 条只规划的用例 ×2 | 基线 | 6.1s | 35.6s | 36.2s |
| 同上 | 降档 | 9.2s | 37.1s | 63.4s |

- 生成组 P50 降 **31 秒**（−61%），最大 84.3s → 36.0s；与 direct 实测一致。
- 只规划的对照组 P50/P95 差异属模型噪声（请求体与基线逐字节一致）；
  降档臂里 V-N4 单次规划 63.4s 是模型自身长思考，不是本次改动引入。
- 整体 P95 **56.9s → 36.9s（−35%）**；剩余尾部来自规划阶段思考（本方案有意不动）。
- 唯一未完成是 V-N8 第 2 轮：模型把源文档读成 **M1（机密）**，网关按「机密不能在云侧生成」
  正确拒绝（`blocks: 生成拒绝`），属**计划漂移**，不是误拦、也不是降档引起。
- 生成正文：direct 实测同一命令 947–1364 token → 54–97 token，仍是完整纪要。

**与 v4.1 旧数的关系**：v4.1 的 P50 23.7s / P95 90.6s（48 次）跑在 v0.55.0 之前，
当时投屏/转写仍调模型；本轮基线已含 v0.55 模板规划（V-N12/V-N14 为 0s），
且环境/并发不同。**绝对数不与 v4.1 横比，归因只看本轮两臂。**

复现：

```bash
cd prototype
node eval/run.cjs --llm=http --split=validation --kind=normal --tiers=full --repeat=2 --out=out/eval-tail-base
SAFE_OFFICE_LLM_GENERATE_REASONING_EFFORT=low \
  node eval/run.cjs --llm=http --split=validation --kind=normal --tiers=full --repeat=2 --out=out/eval-tail-low
```

### 4.1 分项计时：剩余长等待在规划阶段（2026-11-21）

评测报告现在记录**每次模型调用**的耗时，并按正常任务列出最慢的 5 轮
（总耗时 / 规划 / 生成）。用当前 v0.56 跑 validation 正常集 32 次（16 条 × 2 轮）：

- **32/32 完成、0 故障**；P50 **10.1s** / P95 **35.3s** / 最大 **60.1s**。
- 调用级：规划 28 次，P50 10.1s / P95 34.3s / **最大 60.1s**；
  生成 8 次，P50 4.0s / **P95 7.2s / 最大 7.4s**。

| 最慢 5 轮 | 总耗时 | 规划 | 生成 |
|---|---:|---:|---:|
| V-N11 #0 | 60.1s | **60.1s** | 0s |
| V-N9 #0 | 40.2s | 35.9s | 4.3s |
| V-N5 #1 | 31.2s | **31.2s** | 0s |
| V-N9 #1 | 31.0s | 28.3s | 2.6s |
| V-N5 #0 | 27.8s | **27.8s** | 0s |

结论：**生成段已被压到 7.4s 以内；剩余长等待全部来自规划阶段**（60.1s 的长尾就是一次规划调用）。
再往下压只能动规划思考档位，而 §2 的 A/B 已证明它会改变计划（V-N5 多一步 summarize），
需要单独做精度权衡，不能顺手开。

证据：`ws63/logs/eval-normal-phase-20261121/`（`eval-results.json` + `eval-report.html`）；
复现：`node eval/run.cjs --llm=http --kind=normal --split=validation --tiers=full --repeat=2 --out=out/eval-normal-phase-real`。

> 并发保护：真实模型评测启动时写 `out/.eval.lock`（pid/开始时间/输出目录），
> 同一账号第二个评测直接报 `EVAL_BUSY` 并退出；进程已死或锁损坏时自动接管。
> 这次两臂 A/B 遇到的「卡在 V-N4/V-N5」就是并发争用，锁可避免再次发生。
> Mock 评测不经过模型，不加锁。

## 5. 边界

- 单模型（GLM-5.3-Flash）实测；其它模型的 `reasoning_effort` 支持情况需单独验证，
  所以默认不开启，只在 config.env 显式配置。
- `reasoning_effort=low` 不保证思考为 0（实测 0–105 token），只是显著压缩；
  网关若忽略该字段，行为会退回默认思考，不会报错。
- 输出上限 `max_tokens` 默认不设：实测 1024 会截断长纪要（正好停在 1024），
  需要按模型与文稿长度另测，不能拿来做“固定字数”保证。
- 降档只影响生成文稿的篇幅与耗时，不改变闸门、令牌、计划校验与确认路径。
