# 硬件结构化摘要（2026-11-17）

> 把挑战帧从“只有一段摘要文字”升级成**结构化字段**：收件人、密级、附件数随帧下发，
> 板端按这些字段生成分页界面，不依赖 Agent/主机写的说明文字。
>
> 结论：协议 v2 与固件分页已实现，PC 侧 **619 测试（617+2 跳过）**全绿；
> 真机端到端（批准/取消/执行）通过，B 串口日志确认字段到达；
> **OLED 三页已由操作者肉眼确认**（TO / LEVEL / ATTACH / HASH 均正确，2026-11-17）。

## 1. 动机

旧实现里，确认端只能看到 `summary` 一段文字（最多 96 字节）。文字可能被截断、也可能
不能覆盖关键字段。这一刀让屏幕内容**由操作结构生成**：

- 收件人/对象（`recipient`）
- 密级（`level`：公开/内部/机密）
- 附件数量（`attachment_count`）
- 目标哈希（`target_hash`，已存在，取前 6 字节上屏）

## 2. 协议 v2

`ws63/protocol.h`：`PROTO_VERSION = 0x02`。CHALLENGE payload 在原有字段后追加：

| 偏移（payload 内） | 长度 | 字段 |
|---|---|---|
| 原有 | … | task_id/nonce/action/target_hash/issued_at/expires_at/summary_len/summary |
| 66 + summary_len | 1 | `recipient_len`（≤32） |
| … | ≤32 | `recipient`（可打印 ASCII） |
| … | 1 | `level`（0=公开 1=内部 2=机密） |
| … | 1 | `attachment_count`（0–255） |

- MAC 覆盖新增字段；长度非法、非 ASCII 收件人、level>2 一律拒绝；
- **版本号升到 2**：新旧固件/主机不能混跑，必须一起更新；
- 配网帧（0x10/0x12）是独立小协议（版本 1），**不受影响**；
- 最大 CHALLENGE 帧 = 10 + 69 + 96 + 32 + 32 = 239 字节，SLE MTU 251 内。

Node 侧 `src/ws63-protocol.cjs` 与浏览器 `public/sfc1-browser.js` 同步更新；
`NearfieldConfirmer` 从冻结操作直接取 `recipient`/`level`/`attachments.length`
（设备名含中文时替换为 `?` 上屏）。

## 3. 板端分页

`board_confirm_m3.c`：待确认任务存在时，OLED 每 **1.5 秒**轮播 3 页：

| 页 | 内容 |
|---|---|
| 1/3 | `WS63 CONFIRM` + 动作（SEND EXT/DELETE/PRINT/DEVICE）+ `TO:<recipient>` + 按键提示 |
| 2/3 | `LEVEL:PUBLIC/INTERNAL/CONFIDENTIAL` + `ATTACH:<n>` + `2/3 按键提示` |
| 3/3 | 摘要第二段 + `HASH <前 6 字节 hex>` + `3/3 按键提示` |

按键语义不变：**短按批准、长按取消**；分页不影响 TTL 与重放窗口。

## 5. 边界与未做

- 屏幕分页已由操作者肉眼确认（三页内容正确）；但只验证了一个场景（收件人 ASCII、内部级、0 附件），
  中文收件人/多附件/长摘要的显示未逐一验证；
- 收件人为非 ASCII（中文设备名）时以 `?` 占位，不是原文；
- 附件数只表示**数量**，屏幕不显示附件名/哈希（空间不够，后续可加分页）；
- 协议 v2 与 v1 不兼容：现场两块板与 PC 工具必须同版本；
- 摘要文字仍上屏（第 3 页），但关键字段取自结构，不依赖文字。
