# M3' 业务帧上 SLE（2026-11-16）

> 接续 [docs/73](73-M2双板SLE准备-2026-11-14.md) §9：M2 只验了链路存活，PC↔B 的 SFC1 业务帧
> 仍走 UART。本轮把 **CHALLENGE/DECISION 搬上 SLE**，A 板作**不持钥中继**。
>
> **结论：真机端到端通过**——PC 只接 A 的串口，挑战经 SLE 到 B，B 按键后决策原路回 PC，
> MAC 校验与绑定检查全部由原有状态机完成。批准、取消两条路径都过。

## 1. 拓扑与职责

```
PC ──UART(COM11)──> A（exec / SLE client）
                      │  CHALLENGE 原样转发（不解码、不验签）
                      ▼
                    B（confirm / SLE server，COM12）
                      │  解码 + 验 MAC + OLED + KEY2
                      ▲  DECISION 原样回传
PC <──────────────────┘
```

| 板 | 角色 | 持钥 | 做的事 |
|---|---|---|---|
| A | exec / client | 只有自己的钥匙（本轮未配网） | UART↔SLE 转发 CHALLENGE/DECISION；自己的 ACTUATOR 仍在本地验签执行 |
| B | confirm / server | B 的钥匙（本轮已配网） | 原有 SFC1 校验、按键确认、回决策 |

> 密钥体系不变：A 不持有 B 的钥匙；PC 仍用 B 的钥匙发挑战、验决策。
> A 是通道，不是安全边界。

## 2. 分流：`ws63/sfc1_route.c/h`

SLE 传输上现在同时跑两类帧，靠 magic 分流：

| magic | 帧 | 去向 |
|---|---|---|
| `SFCL` | 16B 心跳 | `link.c` 状态机 |
| `SFC1` | 变长业务帧 | 板端 `handle_frame()`（B）或原样转发 UART（A） |

实现要点：

- 4 字节 magic 判别窗口，未命中滑动 1 字节继续找；
- 业务帧按 header 的 length 字段（含 32B MAC）组装，长度非法即丢弃并重新同步；
- 分流只做帧边界，不解析业务语义、不校验 MAC；去重/重放仍在 SFC1 状态机里；
- 纯 C、无 SDK 依赖，PC 侧可测（`ws63/test_route.c`）。

## 3. 板端改动（`board_confirm_m3.c`）

| 改动 | 说明 |
|---|---|
| `g_sle_route` + `sfc1_route_init/feed` | SLE 环形队列的字节先过分流，再分别进心跳/业务处理 |
| `handle_frame(..., int via_sle)` + `pending_t.via_sle` | 记住挑战来源；决策**原路返回**（SLE 来的回 SLE，UART 来的回 UART） |
| `relay_to_sle()` | 只在 `transport_up` 时发送；失败只记日志，不改心跳状态机 |
| `feed_byte` 出口 | A 角色且类型为 CHALLENGE → 转发到 SLE（链路断开则丢弃并打印）；其余类型本地处理 |
| 收包分支 | A：业务帧写回 UART（DECISION 等）；B：业务帧进 `handle_frame(...,1)` |

> 单板 M3（`SFC1_WITH_LINK=0` 或链路未连）行为不变：UART 挑战仍由本板处理、决策仍回 UART。
> `pending.via_sle` 是逐任务字段，不会把直连 UART 的挑战误发到 SLE。

### 5.3 双板「确认在 B、执行在 A」（同日补做）

`serial-confirm.cjs` 新增 `--actuator-device`：确认通过后，再用**执行端 A 的钥匙**发 SFC1 执行帧，
A 验签/查重放后驱动 IO12 并回 ACK。挑战与执行用两把不同的钥匙，是双板拓扑的完整业务闭环。

```bash
node serial-confirm.cjs --port COM11 --device ws63-B \
  --to partner@example.com --subject "M3-double actuator" --ttl 90 --timeout 75000 \
  --actuator-device ws63-A --actuator-pin 12 --actuator-level 1
```

### 5.4 配网与探活也走 SLE（同日补做）

目标：**PC 只接 A 的口**就能给 B 配网和探活，B 只用 OLED 看配对码。

A 的转发策略（`relay_should_forward`）：

| 类型 | 规则 |
|---|---|
| CHALLENGE `0x01` | 总是转发（A 不持 B 的钥匙） |
| PING `0x20` | 用**本板钥匙验 MAC**：验得过是给 A 的，本地回 PONG；否则转发给 B |
| PROV INIT/COMMIT `0x10/0x12` | 仅当 A **已配网**时转发；新板必须先直连完成首次配网 |
| ACTUATOR 等 | 本地处理 |

回包统一走 `send_reply()`：SLE 来的请求原路回 SLE，UART 来的回 UART。

| 用例 | 结果 |
|---|---|
| A 直连配网（`adcbc595`） | ✅ `device_id=1d889565…` |
| **B 经 A 配网**（`2dc0ea15`，PC 只开 COM11） | ✅ INIT/CHALLENGE/COMMIT/OK 全过，`device_id=e3e890b6…` |
| `npm run ping -- --port COM11 --device ws63-A` | ✅ 本地 PONG |
| `npm run ping -- --port COM11 --device ws63-B` | ✅ 中继 PONG |
| 配网后确认+执行回归 | ✅ `decision=1` / `status=0 pin=12 level=1` |

> **坑（已修）**：PING 帧**没有 device_id**（payload 只有 16B nonce），一开始按 offset 10 读 id
> 会把 A 自己的 PING 也转给 B，表现为「A 本地 PING 超时、B 中继正常」。改为钥匙验 MAC 后两条路径都对。

新增工具：`prototype/scripts/ping-device.cjs`（`npm run ping -- --port COM11 --device ws63-B`）。
证据：[`ws63/logs/m3p-prov-relay-20261116.txt`](../ws63/logs/m3p-prov-relay-20261116.txt)。

## 6. 安全边界（材料里必须如实写）

- **A 不是安全边界**：它不持钥，不能伪造 DECISION（没有 B 的密钥）；
  但 CHALLENGE 的摘要明文经过 A，**中继方可读摘要**——不能把 A 描述成"保密通道"。
- 决策的 MAC、任务/nonce 绑定、过期与重放仍由原有 SFC1 状态机在 PC/B 两端完成；
  本轮没有放宽任何校验。
- 心跳仍未认证；SLE 本地地址仍是演示固定值（`02:53:46:43:31:xx`），见 docs/73 §8。
- WiFi 共存证据只覆盖**扫描态**：没有连 AP、没有 IP 层、没有数据业务；
  不能据此宣称「WiFi 业务与 SLE 共存稳定」，也没有 >1h 数据。
- 双板执行已闭环（§5.3）：PC 用 A 的钥匙发 ACTUATOR，A 验签/查重放后驱动 IO12 并回 ACK。
  但仍**没有继电器/锁体实物**——ACK 只证明「板子执行了引脚动作」，不等于真实开锁。
- 两把钥匙都是演示级 PSK，存在设备表与板端 NV 里；不是 HUKS/TEE，也没有安全分发。
- 配网中继依赖 **A 已经配网**：A 自己是新板时必须先直连 UART 配网（PROV 帧在 A 未配网时
  不会转发）。A 重烧后 NV 被清，需要重新走这一步。
- 中继配网不改变信任模型：临时配对码仍由 B 显示/校验，A 只是转发字节，不能伪造 COMMIT。
- **设备身份已按角色区分**（exec=`ws63-A` / confirm=`ws63-B`），两板 `device_id` 不同。
- **KEK**：A 板已 `kek-adopt` 并在重配网后进入 `provisioned v2/kek`；B 板（新板）未烧 KEK，
  仍是 v1 明文记录。整包重烧后 A 会回到 KEK 孤儿状态，需先 `kek-adopt` 再配网（docs/72 §5）。

### 5.5 30 分钟长稳（2026-11-16 21:34–22:04，无 WiFi）

每 5 分钟一轮：PING A（本地）、PING B（经 A 中继）、两端 `link-status`，共 6 轮。

| 指标 | 结果 |
|---|---|
| 心跳 | A `tx 709 → 2297`、B `tx 1018 → 2606`，全程 `bad=0` |
| 断链/超时（本轮新增） | A `up=1 down=0 timeout=0 send_fail=0`（无新增） |
| PING | 12/12 通过（6 次本地 + 6 次经 SLE 中继） |
| B 的 `up=3 down=2 timeout=2` | 长稳前（A 板重烧/复位）留下的计数，6 轮采样不变，不是本轮断链 |

> 这是 **30 分钟**，材料里只能写「短时稳定」，不能写「>1h 稳定」。
> WiFi 与 SLE 共存未测：当前固件不启用 WiFi。

### 5.6 WiFi 扫描 + SLE 共存（2026-11-16，30 分钟）

新增可选构建 `--wifi`（`SFC1_WITH_WIFI=1`）：A 板开 WiFi STA，每 10 秒扫描一次，与 SLE 心跳并行。
**只扫描，不连 AP、不配 IP、不传数据**——测的是射频共存，不是 WiFi 业务共存。

| 时间 | WiFi | A（exec） | B（confirm） |
|---|---|---|---|
| 10 min | `scan #75 ret=0` | `tx=754 rx=755 bad=0` | `tx=762 rx=761 bad=0` |
| 20 min | `scan #138 ret=0` | `tx=1386 rx=1387 bad=0` | `tx=1394 rx=1393 bad=0` |
| 30 min | `scan #201 ret=0` | `tx=2017 rx=2018 bad=0` | `tx=2026 rx=2025 bad=0` |

- 全程 `up=1 down=0 timeout=0 send_fail=0`；3 轮 PING（本地+中继）全过。
- **30 分钟短时共存**：不能写「>1h 共存稳定」；原计划 70 分钟采样被宿主内存压力终止，
  没有 >1h 数据。
- 不能写「WiFi 数据业务与 SLE 共存通过」：没有 AP、没有 IP、没有数据流。
