# 性能与资源度量（v0.46，2026-11-03）

> 补上官方答题要求中的「时延 / 资源」度量：新增可复现的 HTTP 压测 harness，
> 覆盖读请求、命令请求、混合场景，输出 p50/p95/p99、吞吐与 RSS。
> **边界**：本机单进程、MockLLM、内存 SQLite；数字只代表这套环境，不是生产容量承诺。

## 1. 怎么跑

```bash
cd prototype
npm run bench                                  # 默认 mixed / 10 并发 / 100 请求 / 内存库
node bench/load.cjs --scenario=read --concurrency=50 --requests=500
node bench/load.cjs --scenario=command --concurrency=20 --requests=100 --json=1
node bench/load.cjs --scenario=mixed --concurrency=5 --requests=20 --store=file
node bench/load.cjs --scenario=read --concurrency=10 --duration=30
```

- `scenario`：`read`（GET /api/state）、`command`（POST /api/commands，执行内网纪要样例）、`mixed`（70% 读 / 30% 命令）
- `store`：`memory`（默认）或 `file`（真实 SQLite + 审计落盘，临时目录，跑完删除）
- `duration`：按秒数持续压测（soak），与 `requests` 二选一；结果里的 `requests` 是实际完成数
- 超时/中断：`timeoutMs` 到点后 `AbortController` **主动取消在途请求**，工作循环退出，不会继续空跑
- 延迟统计：固定容量蓄水池（默认 20000，`--max-samples=` 可调）；超过容量后百分位是抽样估计，
  结果里 `latencySeen` / `latencySamples` / `approximate` 如实标注
- 结果同时写 `prototype/out/bench/bench-<时间>.json`（`out` 已 gitignore）；RSS 每秒采样，报告峰值
- 冒烟测试：`test/bench.test.cjs`（读/命令/超时取消/有界统计）

### 2.1 真实 SQLite + 审计落盘（`--store=file`）

| 场景 | 并发 | 请求 | 成功 | 吞吐 (req/s) | p50 | p95 | p99 | max | RSS Δ |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| read | 5 | 30 | 30 | 379.4 | 4.80 | 19.71 | 28.95 | 28.95 | +19.7 |
| mixed | 5 | 20 | 20 | 102.5 | 57.24 | 75.52 | 75.52 | 75.52 | +13.2 |

- 每次命令都写 SQLite（operations/outbox/events）并追加审计 JSONL + 检查点；mixed 吞吐从内存库的 ~420 降到 ~102 req/s，属于预期。
- 文件模式只测了短跑；未测磁盘打满、SSD/HDD 差异、WAL 增长。

### 2.2 长时间运行（soak）

| 场景 | 存储 | 并发 | 时长 | 完成请求 | 吞吐 | p50 | p99 | RSS 峰值 | 结束 RSS |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| read | memory | 10 | 10s | 52,032 | 5195.9 | 1.66 | 9.78 | 282.0 MB | 259.8 MB |
| read | memory | 10 | 30s | 162,990 | 5430.2 | 1.61 | 9.64 | 293.6 MB | 276.5 MB |
| mixed | memory | 10 | 10s | 1,280 | 126.3 | 78.22 | 143.76 | 269.7 MB | 269.7 MB |
| mixed | memory | 10 | 5s | 880 | 172.5 | 57.65 | 113.43 | 259.3 MB | 259.3 MB |

- RSS 在 5–30s 内稳定在 **~260–294MB**，请求数从 880 到 163k 没有线性增长；
  主要是 HTTP/undici 连接缓冲与 V8 堆高水位，不是业务数据无界累积。
- **这不能证明“无内存泄漏”**：没有做小时级 soak、没有强制 GC、没有对 operations/audit 表做增长曲线；
  后续如需结论，应加 `--expose-gc` 与更长时间采样。
- read 30s 16.3 万请求 0 失败，说明读路径在高并发下稳定；command 受 `_runChain` 串行化限制。
- **口径说明**：v0.46.2 起延迟样本改为 20k 容量蓄水池，soak 的 RSS 不再被“保存每个请求耗时”撑大；
  上面 2.2 的 RSS 数字来自 v0.46.1（旧实现），只作趋势参考，不作为无泄漏结论。

## 3. 怎么读这些数字

- **读路径**：50 并发下 1.7k req/s，p99 < 70ms；`/api/state` 只做内存聚合，没有 I/O。
- **命令路径**：吞吐稳定在 ~208 req/s；并发从 5 提到 20，p50 从 17ms 升到 91ms。
  原因是 `ConsoleService.runCommand` 用 `_runChain` **串行化**命令，避免共享 runtime/审计链并发写坏；
  这是安全一致性优先的设计，不是性能缺陷。
- **混合场景**：30% 命令会把读请求一起排队，50 并发 p50 升到 132ms；对演示/小团队足够。
- **RSS**：500 请求后增长约 42MB，主要来自 HTTP 连接、审计条目与操作记录；**未做长时间泄漏测试**，
  不能据此宣称“无内存泄漏”。
- **未测**：真实 SQLite 落盘、真实 SMTP、真实模型、TLS 反向代理、多机网络。
  真实模型时延通常远大于本 harness 的进程内开销（见 docs/40/48 的评测时延）。

## 4. 结论与后续

- 当前形态适合**单机演示 / 小团队（数十并发）**；没有发现错误率或尾延迟失控。
- **落盘代价明确**：mixed 从 ~420 req/s（内存）降到 ~102 req/s（SQLite + 审计 JSONL），
  这是“可审计”换来的成本；需要更高吞吐时优先考虑审计批量写/异步落盘，而不是去掉审计。
- 若未来要提升命令吞吐：按租户/工作区分片 runtime、审计批量落盘、把命令队列做成可观测指标；
  **不建议**为了吞吐去掉串行化（会破坏审计链与共享状态的一致性）。
- 内存：30s soak 已到平台期，但**未做小时级泄漏测试**，材料只能写“短时压测稳定”，不能写“无泄漏”。
- 真机/生产环境压测需要单独排期；本报告只覆盖应用层。

## 5. 复现要求

- Node 24、Windows 11（本机）；Linux 数字会不同。
- 关闭真实 SMTP/IMAP/模型/自动回信（harness 用内存库 + MockLLM + FakeMailer）。
- 每次运行都是独立进程；不要在同一进程里连续跑多轮后比较 RSS。
