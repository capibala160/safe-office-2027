# 性能与资源度量（v0.46，2026-11-03）

> 补上官方答题要求中的「时延 / 资源」度量：新增可复现的 HTTP 压测 harness，
> 覆盖读请求、命令请求、混合场景，输出 p50/p95/p99、吞吐与 RSS。
> **边界**：本机单进程、MockLLM、内存 SQLite；数字只代表这套环境，不是生产容量承诺。

## 1. 怎么跑

```bash
cd prototype
npm run bench                                  # 默认 mixed / 10 并发 / 100 请求
node bench/load.cjs --scenario=read --concurrency=50 --requests=500
node bench/load.cjs --scenario=command --concurrency=20 --requests=100 --json=1
```

- `scenario`：`read`（GET /api/state）、`command`（POST /api/commands，执行内网纪要样例）、`mixed`（70% 读 / 30% 命令）
- 结果同时写 `prototype/out/bench/bench-<时间>.json`（`out` 已 gitignore）
- 冒烟测试：`test/bench.test.cjs`（2 并发 × 6 读；1 并发 × 4 命令）

## 3. 怎么读这些数字

- **读路径**：50 并发下 1.7k req/s，p99 < 70ms；`/api/state` 只做内存聚合，没有 I/O。
- **命令路径**：吞吐稳定在 ~208 req/s；并发从 5 提到 20，p50 从 17ms 升到 91ms。
  原因是 `ConsoleService.runCommand` 用 `_runChain` **串行化**命令，避免共享 runtime/审计链并发写坏；
  这是安全一致性优先的设计，不是性能缺陷。
- **混合场景**：30% 命令会把读请求一起排队，50 并发 p50 升到 132ms；对演示/小团队足够。
- **RSS**：500 请求后增长约 42MB，主要来自 HTTP 连接、审计条目与操作记录；**未做长时间泄漏测试**，
  不能据此宣称“无内存泄漏”。
- **未测**：真实 SQLite 落盘、真实 SMTP、真实模型、TLS 反向代理、多机网络。
  真实模型时延通常远大于本 harness 的进程内开销（见 docs/40/48 的评测时延）。

## 4. 结论与后续

- 当前形态适合**单机演示 / 小团队（数十并发）**；没有发现错误率或尾延迟失控。
- 若未来要提升命令吞吐：按租户/工作区分片 runtime、审计批量落盘、把命令队列做成可观测指标；
  **不建议**为了吞吐去掉串行化（会破坏审计链与共享状态的一致性）。
- 真机/生产环境压测需要单独排期；本报告只覆盖应用层。

## 5. 复现要求

- Node 24、Windows 11（本机）；Linux 数字会不同。
- 关闭真实 SMTP/IMAP/模型/自动回信（harness 用内存库 + MockLLM + FakeMailer）。
- 每次运行都是独立进程；不要在同一进程里连续跑多轮后比较 RSS。
