# 确认 → 执行 → 留档 最小闭环（v0.10）

更新：2026-10-17（v0.11 注记 2026-10-18）。范围：本地 Node + SQLite；**未接**真实模型、预览页、真实邮件服务。**WS63 确认适配器已在 v0.11 接入（虚拟设备；串口/SLE 未接）**，见 [WS63 确认适配器](11-WS63确认适配器.md)。

> 目标：把“确认”和“执行”绑到同一条不可变记录；处理邮件超时的不确定性；本地留档。
> 这是评估建议里的第一优先项，硬件未通时用模拟确认即可。

---

## 1. 组件

| 文件 | 职责 |
|---|---|
| `prototype/src/operation.cjs` | 冻结操作记录：`bodyHash` / `attachmentHashes` / `operationHash`；执行前校验；状态迁移 |
| `prototype/src/store.cjs` | `node:sqlite` 持久化：`operations` / `outbox` / `events`；本地事件哈希链 |
| `prototype/src/mailer.cjs` | `FakeMailer`（测试/演示）+ `HttpMailer`（Idempotency-Key + 超时分类） |
| `prototype/src/fulfillment.cjs` | `prepare` / `confirm` / `send` / `reconcile` / `recoverInFlight` |
| `prototype/src/nearfield-confirm.cjs`（v0.11） | WS63 确认适配器：SFC1 CHALLENGE/DECISION + 设备/操作绑定 + 虚拟设备（`confirmWithFulfillment`） |

## 2. 操作记录（同一条记录）

字段：

```
operationId, taskId, action, protocolAction, tool, recipient, subject,
body, bodyHash, attachments[{name,sha256,size}], attachmentHashes,
sourceDocIds, level, createdAt, expiresAt, modelId, planHash,
operationHash, state
```

- `operationHash = SHA-256(canonical(记录字段))`，不含 `body` 本身，含 `bodyHash`
- **WS63 挑战里的 `target_hash` 直接装这 32 字节**
- 设备确认的是 `operationHash`；发送前服务重新计算并比对
- 正文、收件人、附件、来源、密级、模型/计划任一变化 → 校验失败，必须重新确认

## 3. 状态机

**操作**：

```
frozen → confirmed → executing → executed
   │         │            └────→ failed
   ├───────→ rejected
   └───────→ expired；confirmed → expired / failed
```

**发件箱**：

```
pending → sending → sent
              ├──→ failed（4xx/明确拒绝，终态；重试须新建记录）
              └──→ unknown（超时/断网/5xx；禁止自动重试）
unknown → sent / failed（人工 reconcile）
```

## 4. 邮件不确定性

- **timeout / network / 5xx** → `unknown`：可能已被接收，**绝不自动重试**
- **4xx（除 408/429）** → `failed`：明确失败，终态
- 进程重启：`sending` → `unknown`（`recoverInFlight`），等待人工核对
- `reconcile` 是唯一消除 `unknown` 的入口
- `HttpMailer` 要求服务端支持 `Idempotency-Key`；**SMTP 没有标准幂等键，本项目不实现 SMTP**
- SQLite 只保证本地状态与审计，**不保证外部邮件服务只执行一次**

## 5. 验收测试（`prototype/test/fulfillment.test.cjs`，9 项；v0.10 时全套 109 项，v0.11 起 123 项，v0.12 起 157 项，v0.13 起 173 项）

1. 操作记录冻结/校验/篡改/非法状态迁移
2. SQLite 记录不可覆盖、同一 operationHash 只入队一次、事件链篡改可检出
3. 确认哈希必须匹配；发送成功 → executed；重复发送不重复调用
4. 确认后改正文 → 发送前拒绝，邮件服务零调用
5. 服务端已接收但客户端超时 → unknown；不自动重试；人工核对 → executed
6. 明确拒绝 → failed；同一记录不能复用
7. 过期 → 确认阶段拒绝并标记 expired
8. 进程中断 → sending → unknown；恢复后不自动发送
9. HttpMailer：成功 / 4xx / 5xx / 超时分类

## 6. 边界

- 正文以明文存 SQLite；生产需加密/最小化留存
- `confirm(operationId, {confirmedHash})` 仍是可信进程内 API，调用方可以绕过适配器直接交哈希
- v0.11 已接 **WS63 确认适配器（虚拟设备）**：真实 SFC1 帧/HMAC/设备与操作绑定；串口/SLE、真实按键/OLED 未接
- 运行时闸4 仍使用 `ConfirmationService` 进程内模拟确认，不能声称运行时已接 WS63
- 预览页、真实模型、真实邮件服务未接
- 事件哈希链与 SQLite 同文件；检查点必须独立保护，不能证明整库未被替换
- 不提供距离证明、本人身份认证或防中继保证
