# 持久化、模型注入与工作区版本号（v0.15）

> 2026-10-29 建立。来源：对 `hackathon/workbench` 的外部评审，其中「状态持久化」「真实模型可注入」「并发/过期结果」三条在主线原型里同样成立（主线已有「来源溯源」，见 §5）。本轮只改 `prototype/`，工作台未动。

---

## 1. 之前的问题

| 问题 | 位置 | 后果 |
|---|---|---|
| 操作库写死内存 | `console-service.cjs`：`new OperationStore(':memory:')` —— 而 `store.cjs` 本来就支持文件路径 | 重启清空；`recoverInFlight()` 写好了却**没有调用点** |
| 审计链只在内存 | `AuditLog` 有 `save/load`，但没人调用 | 重启后审计全丢 |
| 模型写死 Mock | `new MockLLM()` 硬编码 | 真实模型只能靠改代码；界面/报告里的模型标注也不可信 |
| 重置与在途运行 | `reset()` 重建工作区，但在途命令继续跑 | 旧命令的结果落进新工作区，重置意图被吃掉 |

---

## 2. 本轮改动

### 2.1 操作库落盘

- `ConsoleService` 新增 `storeFile`（默认 `:memory:`）。
- 文件模式下启动自动调用 `FulfillmentService.recoverInFlight()`：上次进程中断时还在 `sending` 的记录**统一转 `unknown`**，写一条 `恢复` 审计，**禁止自动重试**，只能走 `reconcile` 人工核对。

### 2.2 审计链落盘

- `AuditLog` 构造器新增 `onAppend` 回调，每次 `append` 后落盘。
- 两份文件：`audit.json`（entries + checkpoint）与 `audit.json.head`（独立检查点）。恢复时 `AuditLog.load(file, checkpoint)` 校验整链；**校验失败 → 丢弃旧链、从新链开始，并记一条 `审计恢复失败`**。
- **边界**：两份文件在同一磁盘上，不抵抗有删改权限的攻击者；它只能发现"整链被替换/改写"。真正独立需要把 checkpoint 存到别处（另一台机器、签名服务等）。

### 2.3 模型可注入

- `llm.cjs` 新增 `createLlmFromEnv()`：配了 `SAFE_OFFICE_LLM_ENDPOINT` + `SAFE_OFFICE_LLM_KEY` 就用 `HttpLLM`，否则退回 `MockLLM`。
- `ConsoleService` 新增 `llm` 参数，直接注入任意实现（接口只需 `plan(command, blocks)` / `generate(command, blocks)`）。
- `getState().model` 与治理报告里的模型字段改为**如实反映实际实现**，不再固定写 `MockLLM（演示）`。

### 2.4 工作区版本号（重置与在途结果）

- `generation` 在 `reset()` 时自增；`_executeCommand` 在 `await runtime.runCommand()` 之后比对版本。
- 不一致 → 返回 `{ ok:false, stale:true, reason:'RESET_DURING_RUN' }`，**不写操作、不写审计、不进运行列表**。
- 文件模式下 `reset()` 连同 `.db` / `-wal` / `-shm` / 审计文件一起删除，避免旧操作在下次启动时"复活"。

## 3. 怎么用

```bash
# 内存模式（默认，行为与 v0.14 一致）
npm start

# 落盘：操作库 + 审计链
SAFE_OFFICE_STORE_FILE=./data/ops.db SAFE_OFFICE_AUDIT_FILE=./data/audit.json npm start

# 真实模型（OpenAI 兼容端点）
SAFE_OFFICE_LLM_ENDPOINT=https://... SAFE_OFFICE_LLM_KEY=... SAFE_OFFICE_LLM_MODEL=... npm start
```

启动横幅会打印当前模型、持久化路径，以及 `恢复` 了多少条在途记录。

## 4. 验证

新增 7 项测试（`test/persistence.test.cjs`，**全仓 206 项全绿**）：

| 用例 | 断言 |
|---|---|
| 文件库重启 | 同一 `operationId` 重启后仍在且状态 `frozen`；审计条目数一致、链自校验通过 |
| 审计篡改 | 改一条 detail → 恢复被拒，新链只含 `审计恢复失败` 一条 |
| 在途恢复 | `sending` → `unknown`，`lastError` 含"待核实"，`send()` 不会重试，审计有 `恢复` |
| 重置清盘 | 重置后库空；重启后旧操作查不到、审计 0 条 |
| 版本号 | 运行途中 `reset()` → 结果 `stale`，新工作区零操作、零运行 |
| 模型注入 | 注入的 `FakeLLM` 在 `state.model` 里如实出现 |
| 模型选择 | 无端点密钥 → `MockLLM`（local）；有 → `HttpLLM`（cloud） |

HTTP 端冒烟：起服务 → POST `/api/commands` 冻结一条外发 → 关闭 → 重启 → `/api/operations` 仍返回同一 `operationId`。

## 5. 复查修复：确认摘要会挤掉收件人（2026-10-29）

| 项 | 内容 |
|---|---|
| 现象 | `buildSummary` 把 `动作｜主题｜→ 收件人` 整体截断到 96 字节。中文 3 字节/字，长主题能把**收件人整个挤掉**，确认人在手机上只看到主题就点了批准 |
| 修复 | 先保证 `动作｜→ 收件人` 完整可见，主题只吃剩余预算；收件人本身超长时才截收件人（保留「→」） |
| 测试 | `test/nearfield-confirm.test.cjs` 新增「长中文主题不能挤掉收件人」；全套 **207 项全绿** |
| 实测 | 长主题 + `partner@partner-example.com` → `外发｜周例会纪要（草稿）修订版——关于第｜→ partner@partner-example.com`（94B，收件人完整） |

边界没变：摘要只是给人看的展示文本，**不参与 MAC 绑定**——改摘要不影响帧校验。真正约束"发给谁"的是 `operationHash` 与设备/操作绑定。

## 6. 没做的（照实写）

- **来源校验**：主线 `planner.cjs:67-90` 已有（收件人/上传地址必须出现在用户指令里，只出现在外部材料 = 注入诱导 → 移除并记证据），本轮未改，也**不需要**照搬工作台那套。
- **发信与生成稿的绑定**：`runtime.cjs` 只把生成稿命名成 `draft_源ID`，「发送时必须引用 draft_、不能发源文档」目前**只写在提示词里**，没有代码强制。真实模型可能直接把源文档发出去——这是接真模型前应该补的一条规则校验。
- **价格/承诺的风险等级规则**：主线用 `commandLevel` + 五道闸 + 风险计量，没有"关键词提级"这类规则；要不要做取决于评测结论，本轮未加。
- **真实模型跑分**：`HttpLLM` 只是接线通了，**没有用真实模型复跑评测集**，现有 0% 攻击成功率仍是 Mock 机制验证。
- **审计落盘频率**：每次 `append` 都整链重写并校验（O(n²)）。演示规模（几百条）无感；上千条需要改成增量追加。
- **风险计量/业务状态仍在内存**：重启后风险分清零、日历/打印/设备状态丢失。
