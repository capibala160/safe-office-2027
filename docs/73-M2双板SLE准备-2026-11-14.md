## 1. 范围与角色

| 角色 | 板 | SLE 角色 | 职责 |
|---|---|---|---|
| 执行端 A | WS63-A | client | 扫描 `sfc1-confirm`、连接/配对/MTU/服务发现；保留 PC UART（业务中继属 M3'，本轮不做） |
| 确认端 B | WS63-B | server | 广播 `sfc1-confirm`、等待连接；保留 OLED/KEY2/一机一钥 |

两块板烧**同一套源码**的两个角色镜像（编译期开关，见 §5）。M2 只验证**链路存活**；
现有 M3 业务帧（CHALLENGE/DECISION）本轮不改，仍可在**单块确认板 + PC 串口**上验证。
双板拓扑下 PC↔B 的 UART 不再直连，业务帧改走 A 中继属于下一步 M3'。

## 2. 链路帧（16B，固定长度，小端）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0–3 | 4 | magic | ASCII `SFCL`（与业务帧 `SFC1` 区分） |
| 4 | 1 | version | `0x01` |
| 5 | 1 | type | `0x01` HEARTBEAT |
| 6 | 1 | role | `0` 执行端 / `1` 确认端 |
| 7 | 1 | flags | 保留 0 |
| 8–11 | 4 | seq | 每发一帧 +1 |
| 12–15 | 4 | uptime_ms | 发送方开机毫秒数（32 位，49 天回绕） |

**没有 MAC/校验和**：心跳只回答“链路对端还在不在”，不参与任何批准/执行判断。
安全决策必须走 SFC1 的 HMAC 帧（[protocol.h](../ws63/protocol.h)）。

## 3. 状态机与“丢包可恢复”

```
DOWN ──transport_up──> CONNECTED ──收到有效心跳──> ALIVE
  ^                        ^                         │
  │                        └──── 超过 timeout_ms ────┘
  └──────────────── transport_down ────────────────┘
```

- 默认 `heartbeat_ms=1000`、`timeout_ms=3500`（约 3 个心跳周期）。
- **丢失 1–2 个心跳不会掉线**；超过 3500ms 才降为 `CONNECTED` 并记 `timeout_count`。
- 之后**任意一帧有效心跳直接回到 `ALIVE`**，不要求断开重连——这就是“丢包可恢复”。
- 传输层真断（SLE 断开）才走 `DOWN`；重连后从 `CONNECTED` 重新开始，不继承旧存活时间。
- 诊断计数：`tx/rx/bad/gap/stale/up/down/timeout/send_fail`，板端 `link-status` 可查。

SLE 回调运行在 BT 任务上下文，只做 512B 环形队列入队；解析、状态机、OLED、发送都在
`key_task` 主循环，避免在协议栈回调里做耗时操作。

**SLE 本地地址**：本板启动日志一直有 `init_sle_mac failed!`（NV/eFuse 无工厂 SLE MAC），
因此照厂商 `sle_speed` 样例在 `enable_sle` 后显式设置演示地址——
`02:53:46:43:31:02`（confirm）/ `02:53:46:43:31:01`（exec）。该地址只保证两板可发现/可连接，
**不是身份凭据，也不冒充工厂 MAC**。

## 5. 构建

```bash
# 默认 M3（不带 SLE 链路，行为与 docs/72 一致）
node ws63/firmware/build-m3.cjs --build

# M2 确认端 B（SLE server）
node ws63/firmware/build-m3.cjs --link --role=confirm --build

# M2 执行端 A（SLE client）
node ws63/firmware/build-m3.cjs --link --role=exec --build
```

`--link` 必须显式带 `--role`，否则脚本直接报错——防止两块板误烧成同一角色。

M2 构建会把产物另存为：

```
ws63/firmware/out/ws63-liteos-app-m2-confirm.fwpkg
ws63/firmware/out/ws63-liteos-app-m2-exec.fwpkg
```

> `ws63/firmware/out/` 已加入 `.gitignore`；SDK 原始产物路径仍是
> `D:\fbb_ws63\src\output\ws63\fwpkg\ws63-liteos-app\ws63-liteos-app_all.fwpkg`，
> 每次构建都会覆盖，所以两个角色要各留一份。

## 7. 上板验收清单（板到后执行）

前置：
- 两块 FS-Hi3863DB_V2 均能烧录；SW1=0；USB-UART0 115200 8N1。
- 烧**完整 fwpkg 会重写 `ws63_all_nv.bin`**，配网钥匙/nonce 窗口会被清掉；
  KEK 在 eFuse 不受影响，但需要重新配网 + `kek-adopt`（docs/72 §5）。
- 只接一块板时，先烧 confirm 镜像做单板冒烟；**不要**用 client 镜像单板验收（它只会一直扫描）。
- **M2 心跳不依赖配网钥匙**：整包烧完 NV 被清空也能直接验链路；只有顺带验 M3 确认路径时才需要重新配网。

烧录（COM 按实际改）：

```bash
# 推荐：115200 + 工具启动后手按一次 KEY1（2026-11-04 晚更稳的组合）
hsflash.exe write -c ws63 -p COM11 \
  -f ws63/firmware/out/ws63-liteos-app-m2-confirm.fwpkg \
  -b 115200 --before-reset --after-reset --burn-interval 5

# 备选：921600 + 自动切波特率（firmware/README §4；成功率约 50%，失败重试）
hsflash.exe write -c ws63 -p COM11 \
  -f ws63/firmware/out/ws63-liteos-app-m2-confirm.fwpkg \
  -b 921600 --switch-after-loader --before-reset --after-reset --burn-interval 5
```

### 7.1 单板冒烟（确认端 B）

烧 `m2-confirm.fwpkg`，115200 监听并复位：

1. 串口出现 `[SFC1 SLE] local addr 02:53:46:43:31:02`（本地地址兜底）
2. 随后出现 `[SFC1 SLE] role=server ready name=sfc1-confirm`（SLE 启动在 `board_link_init` 内层）
3. 随后出现 `SFC1 LINK: init role=confirm ret=0`
4. 出现 `[SFC1 SLE] announce enable ... status=0x0`
5. 串口发 `link-status` → `state=DOWN transport=down peer=none`
6. 原 M3 功能不回归：短按/长按 KEY2、`efuse`、`kek-status` 正常

### 7.2 双板链路（M2 通过标准）

A 烧 exec、B 烧 confirm，两个 COM 同时监听：

```bash
cd prototype
npm run link:verify -- --a COM_A --b COM_B --seconds 30
```

通过标准：

1. A：`SFC1 LINK: init role=exec ret=0`；B：`init role=confirm ret=0`
2. 两端都出现 `SFC1 LINK: ALIVE peer=...`
3. 两端 `link-status` 的 `rx` 持续增长、`bad=0`
4. **断线重连**：给 B 断电 5s 再上电（或按 KEY1 复位），A 应先打印
   `SFC1 LINK: peer lost (timeout 3500ms)`，B 恢复后 A 再次 `ALIVE`
5. 恢复后 `link-status`：`up>=2`、`down>=1`、`timeout>=1`，无 `send_fail` 持续增长

带重连断言的自动判定：

```bash
npm run link:verify -- --a COM_A --b COM_B --seconds 45 --expect-reconnect
```

### 7.3 常见问题

| 现象 | 排查 |
|---|---|
| 启动日志 `init_sle_mac failed!` | 本板历史日志里**一直存在**（[m3-sfc1](../ws63/logs/m3-sfc1-20261104.txt)）。说明 NV/eFuse 里没有工厂 SLE MAC；固件会在 `enable_sle` 后设置本地演示地址兜底，若 `enable_sle` 仍直接失败，需厂商写 MAC（NV/eFuse）后才能做 SLE |
| 只有 B 有日志、A 一直 scanning | 确认 B 已烧 confirm 且广播名是 `sfc1-confirm`；两块板距离 <1m；A 启动后等 5s（client 有 SLE core ready 等待） |
| `init ret=-1` | 看紧随其后的 `[SFC1 SLE] ... fail` 行；多为 `enable_sle` 失败或服务注册失败 |
| 连上但没有 ALIVE | 检查是否两端都烧了同一角色（脚本会报“角色相同”）；`link-status` 看 `rx` 是否增长 |
| 拔电后不重连 | confirm 端断开后应自动 `sle_start_announce`；exec 端应自动重新扫描。看 `[SFC1 SLE]` 日志 |
| 烧完提示未配置 | 正常：整包烧录清了 NV。按 docs/60 重新配网，再 `kek-adopt` |

## 8. 安全边界（材料里必须如实写）

- 心跳**未认证**：能发 SLE 包的设备可以伪造心跳，只能证明“链路上有东西在响应”。
- SLE 本地地址是**演示固定值**（`02:53:46:43:31:xx`），不是工厂 MAC/设备身份；不能用于身份判断。
- SLE 连通/RSSI **不构成**距离证明、本人身份认证或防中继。
- 批准/执行的唯一依据仍是 SFC1 HMAC 帧 + 冻结操作 + 重放窗口；心跳不能替代。
- 两块板当前仍是**演示密钥/一机一钥**体系；M2 不改变密钥分发模型。
- M2 代码就绪 ≠ M2 完成；在 §7 真机通过前，完成度表里 M2 保持“未做/待补板”。

## 9. 下一步（M3'：把 SFC1 业务帧搬上 SLE）

建议的接力方式（不在本轮实现）：

- A 作为**不持钥中继**：PC → UART → A 按帧类型分流；`CHALLENGE(0x01)` 原样转发到 SLE → B；
  B 的 `DECISION(0x02)` 原样回传 PC。这样 PC↔B 的密钥体系不变，A 无需持有 B 的钥匙。
- `ACTUATOR(0x21)` 仍由 A 用**自己的**钥匙验签后驱动 IO12/IO13。
- 链路层继续用心跳做存活/重连；业务帧到齐后由现有 `feed_byte` 解析，不改协议格式。
