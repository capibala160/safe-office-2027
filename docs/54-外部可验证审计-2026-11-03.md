# 外部可验证审计（Ed25519 检查点签名，v0.46）

> 之前审计链 + HMAC 检查点只能“本机自证”：验证方必须拿到同一个 HMAC 密钥。
> 本轮把检查点改为 **Ed25519 签名**：私钥只在服务端，**公钥可以公开**，
> 任何拿到日志 + 检查点 + 公钥的人都能独立验证，不需要服务端配合。

## 1. 生成密钥

```bash
cd prototype
npm run audit:keygen -- --out=data/keys
# 私钥：data/keys/audit-ed25519-private.pem（0600，勿提交/外发）
# 公钥：data/keys/audit-ed25519-public.pem（可公开）
# keyId：公钥 DER 的 SHA-256 前 16 位
```

也可以不落盘，直接把 PEM 放进环境变量（适合容器 secret）：

```bash
SAFE_OFFICE_AUDIT_ED25519_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\n..."
SAFE_OFFICE_AUDIT_ED25519_PUBLIC_KEY="-----BEGIN PUBLIC KEY-----\n..."
```

## 2. 服务端启用

```bash
SAFE_OFFICE_AUDIT_ED25519_PRIVATE_KEY_FILE=data/keys/audit-ed25519-private.pem
SAFE_OFFICE_AUDIT_ED25519_PUBLIC_KEY_FILE=data/keys/audit-ed25519-public.pem
```

- 启动日志会打印：`检查点签名 → Ed25519（keyId …）`
- 之后每次追加审计，`audit.jsonl.head` / 租户检查点都写成：
  ```json
  { "count": 12, "head": "…", "alg": "Ed25519", "sig": "base64…", "keyId": "…" }
  ```
- 治理页「双链校验」显示签名算法与 keyId。

## 3. 第三方验证（不需要私钥）

```bash
npm run verify:audit -- \
  --audit=data/audit.jsonl \
  --checkpoint=data/audit.jsonl.head \
  --public-key=data/keys/audit-ed25519-public.pem
```

输出：

```
签名：Ed25519（keyId 9e489d984421d69e）
条目：12 · 哈希链 通过 · 检查点 通过 · 签名 通过
结果：通过
```

- 退出码 0 = 通过；1 = 失败
- `--json=1` 输出机器可读结果
- 检查点允许是日志的**前缀**（保存后又追加了新条目），只要 count/head 对得上

验证内容：
1. 整条日志哈希链（seq / prevHash / hash）
2. 检查点 count/head 与日志前缀一致
3. 检查点 Ed25519 签名（keyId 必须匹配公钥）

## 4. 兼容旧检查点

- 旧 `HMAC-SHA256` 检查点仍可读取/校验：保留 `SAFE_OFFICE_AUDIT_KEY` 即可；新追加会改用 Ed25519。
- 如果只配置 Ed25519、旧检查点又没签名，恢复会失败并隔离旧链（不静默降级）。
  迁移顺序：先用旧配置轮转一次 → 再启用 Ed25519。
- 只配置公钥不配置私钥会直接报错（不能签发新检查点）。

## 5. 它证明什么 / 不证明什么

**证明**
- 检查点由持有私钥的一方签发；改动 count/head 而不重签会被发现。
- 配合公开公钥，第三方不需要服务端密钥即可复核。

**不证明**
- **不证明签发时间**：需要时间证明时，另把检查点哈希交给 RFC 3161 时间戳或透明日志（未实现）。
- **不阻止持有私钥的人重写整条链**：他能重新签一份自洽的新链；第三方必须比较**不同时间点拿到的检查点**（或使用外部只追加存储）才能发现。这也是为什么仍建议：
  - 定期把快照导出到外部目录（`SAFE_OFFICE_AUDIT_EXTERNAL_DIR`，见 docs/52）
  - 把检查点哈希另行归档/公示
- 不提供身份认证：只证明“这把私钥签了这份检查点”。
