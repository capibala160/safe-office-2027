# 一机一钥与安全存储：设计稿（2026-11-04）

> **只设计，不改代码。** 目标：把 SFC1 的预共享密钥从"一把演示密钥编译进镜像"
> 改成一机一钥，并尽量利用 WS63 平台能提供的存储保护。
> 相关实现：[docs/11](11-WS63确认适配器.md)、[docs/57](57-M3板端SFC1与串口CLI-2026-11-04.md)、[docs/59](59-运行时闸4接真板-设计-2026-11-04.md)。
>
> **实施进度（2026-11-04，方案 A 第一批已落地并真板验证）**：
> - 协议：`prototype/src/device-provisioning.cjs`（0x10~0x14，含 peek/会话密钥/一次性密钥流，9 项测试）
> - 板端：`sfc1_key_store.c/h`（NV `0x0F02`，64B，HMAC 完整性 tag）+
>   `sfc1_provision.c/h`（临时码、3 次失败上限、10 分钟窗口、TRNG 生成 nonce）
> - 主机：`scripts/provision-device.cjs`（`npm run provision`）；设备表 `prototype/data/devices.json`
>   （**已在 `.gitignore`**，权限 600）
> - **真机结果**：配网成功 `device_id=1d889565919dce48`；**旧 demo-key 挑战被板端丢弃（CLI TIMEOUT）**；
>   新 key 确认 `decision=1`；重启后启动日志 `SFC1 KEY: provisioned (at 24)`，密钥从 NV 恢复
> - 已知迁移细节：换钥后旧 nonce 窗口记录的 tag 验不过 → 启动打印 `SFC1 NV: tag mismatch` 并重置窗口；
>   无害（旧 key 的帧已经在 MAC 层被拒）
> - 仍未做：eFuse 阶段 B；主机侧多设备选择（控制台仍只认单 key）；生产模式硬开关
>
> **复核问题修复（2026-11-04，评审发现 4 项）**：
> 1. **高** 配钥后重启丢重放保护：`mark_used()` 保存 nonce 窗口仍用 `DEMO_KEY`，启动却用 `g_key` 校验。
>    改为保存用 `g_key`；配钥成功时再用新钥重写一次窗口。真机验证：重启打印 `SFC1 NV: restored 3 nonces`。
> 2. **高** 未配置设备仍接受演示密钥挑战：`g_provisioned` 只赋值没用。现在 `handle_frame()` 在配网帧之后
>    直接拒绝普通 CHALLENGE（`SFC1 challenge rejected: UNPROVISIONED`）。真机验证：未配置板对 `--demo-key` 返回 TIMEOUT。
> 3. **中** OLED 配对码显示顺序：`show_pairing()` 原在 `ssd1306_init()` 之前调用、又被待机页覆盖。
>    改为在 key 任务里、OLED 初始化之后按"未配置 → 配对页 / 已配置 → 待机页"显示。
> 4. **中** 配钥回执丢失会丢唯一新钥：主机现在**先写 `devices.pending.json`（600）再发 COMMIT**，收到 OK 后提升到
>    设备表并删除 pending；失败/超时保留 pending，对同一设备重跑会复用该钥匙（`chooseKey` 三条分支有单测）。
>
> **运维事实（重要）**：烧完整 `ws63-liteos-app_all.fwpkg` 会写 `ws63_all_nv.bin`，**配网钥匙和 nonce 窗口会被清掉**，
> 烧完必须重新配网。日常只更新应用时优先用 `hsflash --only-burn` 只烧应用分区（待验证分区名），
> 不要把"烧录后未配置"误判成固件 bug。

### 复核问题修复（第二轮，2026-11-04）

1. **高｜后续配钥覆盖未恢复的密钥**：pending 原先是单条文件。现改为**按 deviceId 多记录**，
   写入 upsert、清除只删本次设备，其它设备的未恢复记录保留；最后一条清掉才删文件。
   单测覆盖"写 A 再写 B → 清 B 后 A 仍在"。
2. **中｜重跑复用走不通**：板端写钥成功后关闭配网窗口，回执丢失时重跑只会超时。
   新增 **PING(0x20)/PONG(0x21)** 探活帧（用设备密钥验签/签名，不依赖配网窗口），
   主机 `--recover` 对每条 pending 发 PING，验过 PONG 才登记到设备表并清 pending。
   **真机验证**：真实设备（正确钥匙）→ `✓ 已验证，钥匙已登记`；假设备（错误钥匙）→ `✗ 无响应，pending 保留`。
3. **中｜新输出目录导致首次配钥失败**：`writePending()` 现在先 `mkdirSync(dirname, { recursive: true })`，
   单测覆盖"嵌套目录不存在也能写"。

固件体积 1,472,296B（含 PING 处理）。519 测试（517 + 2 跳过）、lint 全绿。

## 1. 现状与问题

| 位置 | 现状 |
|---|---|
| 板端固件 | `board_confirm_m3.c` 里的 `DEMO_KEY = 0x42 × 32`，**编译进镜像**；所有板共用 |
| 主机 CLI | `serial-confirm.cjs` / `console-serial-check.cjs` 用 `--demo-key` 或 `--key` |
| 控制台 | `nearfieldKey` 默认 0x42；手机确认端用 `pairingCode` 派生 |
| nonce 窗口 | 已落 NV（M1），但 NV 是明文 |

**后果**：
1. 拿到任意一份固件镜像就能拿到全系统的密钥；
2. 一块板泄露 = 可以伪造**所有**板的确认；
3. 主机侧也是一把钥匙开所有设备，无法区分"哪台设备批的"。

## 2. 平台能力底账（已核对 SDK，不是猜的）

| 能力 | 结论 | 依据 |
|---|---|---|
| HUKS | ❌ **不可用** | `D:/fbb_ws63/src/include` 全量搜索无 HUKS；板端跑的是 LiteOS（`ws63-liteos-app`），不是 OpenHarmony |
| eFuse | ✅ 可读可写，**256 字节**，OTP（只能 0→1） | `driver/efuse.h`：`uapi_efuse_read_buffer` / `uapi_efuse_write_buffer`，byte_number 0~255 |
| eFuse 读保护 | ❌ 未见 | 固件可以读全部 eFuse；`_with_flag` 是写入保护标志，不是读限制 |
| 安全启动/镜像密钥区 | ⚠️ 存在但未启用 | 启动日志 `verify_image_key_area secure verify disable!`、`flash_encrypt disable.` |
| mbedTLS | ✅ | HMAC-SHA256 / SHA-256 已在用 |
| NV | ✅ 明文 | nonce 窗口就在 NV（key `0x0F01`） |

> **关键限制**：WS63 LiteOS 上没有 TEE/HUKS 暴露给应用。任何"设备要用就能算 HMAC"的密钥，
> **只要有代码执行或能读 flash，就能被提取**。所以本设计的定位是：
> **消除共享密钥与镜像内密钥**，而不是承诺"物理不可提取"。

## 3. 威胁模型

| 威胁 | 现状（共享 PSK + 镜像） | 一机一钥（NV） | 一机一钥（eFuse） |
|---|---|---|---|
| 拿到固件镜像 | ❌ 直接拿到 key | ✅ 镜像里没有 key | ✅ 同左 |
| 拿到一块设备并 dump flash | ❌ 拿到同一把 key | ⚠️ 拿到**该设备**的 key | ⚠️ 固件仍可读出该设备 key（无 key ladder） |
| 一块设备被攻破 → 伪造另一块 | ❌ 可以 | ✅ 不行 | ✅ 不行 |
| 重放旧帧 | ✅ 已由 NV 窗口挡住 | ✅ | ✅ |
| 物理侧信道 / 拆芯片 | ❌ 不防 | ❌ 不防 | ❌ 不防 |
| 身份认证 / 距离证明 | ❌ 不提供 | ❌ | ❌ |

## 4. 方案对比

| 方案 | 说明 | 结论 |
|---|---|---|
| **A. 一机一钥 + NV（第一阶段）** | 出厂/首次配对写入 32B 随机密钥到 NV；固件启动加载；主机按 device_id 存钥匙 | ✅ **先做**：无 eFuse 烧写风险，解决"镜像含 key + 共享 key" |
| **B. 一机一钥 + eFuse（第二阶段）** | 密钥或 KEK 写 eFuse；NV 只存密文 | ⏸ **等厂商 eFuse 地图**：写错位可能变砖/关调试 |
| C. HUKS | 平台不支持 | ❌ 不做 |
| D. 出厂固定密钥表 | 工装预置但所有设备相同 | ❌ 不解决共享问题 |

**推荐路线：先 A 后 B。** eFuse 必须拿到厂商的地址分配（chip id / MAC / secure boot key / 用户区）后再动，
且先在**可牺牲的板子**上验证读写；当前只剩一块可用板，绝不能拿它试烧。

## 5. 方案 A 详细设计

### 5.1 密钥与身份

- 密钥：32 字节随机（`crypto.randomBytes(32)`），**每台设备唯一**；
- `device_id`：保持现有派生 `SHA-256("safe-office/ws63/device-id/v1\0" + label)[0..8]`，
  label 仍为 `ws63-A`（一台一板时就是设备名）；
- 主机侧设备表：`device_id ↔ { key, label, provisionedAt, note }`。

### 5.2 板端：密钥存储与加载（NV，key 建议 `0x0F02`）

记录格式（与 nonce 窗口同风格）：

```
magic "SFC1KEY1" | version | flags | provisioned_at | key[32] | tag[16]
tag = HMAC-SHA256(device_secret, 前 N 字节) 的前 16 字节
```

**引导问题**：这时还没有密钥，tag 用什么签？
第一阶段用**设备身份常量**（`device_id` + 固定域串）派生一把"完整性钥匙"——它**不是秘密**，
只防误写/位翻转，不防主动篡改。这一点必须写进材料，不能声称"NV 里的 key 被密码学保护"。

加载逻辑：
1. 读 NV → 校验 magic/version/tag → 有 key：正常模式；
2. 无记录/校验失败：进入**未配置模式**——只接受配网帧，不响应普通 CHALLENGE，
   OLED 显示 `UNPROVISIONED`，串口打印指引；
3. 未配置模式限时（如 10 分钟）后停止接受配网，防止现场被随手配。

### 5.3 配网（provisioning）流程

```
主机 provisioning 工具                     板端（未配置模式）
  |-- 0x10 PROVISION_INIT ---------------->|  生成 16B nonce，回 PROVISION_CHALLENGE
  |<-- device_id + nonce + 板端随机数 ------|
  |-- 0x11 PROVISION_COMMIT -------------->|  校验 HMAC(临时码, 会话) + 写入 NV
  |    (key 用临时码加密)                    |  回 PROVISION_OK / 失败原因
```

- **临时码**：板上丝印/OLED 显示的 6~8 位一次性码，只在本次上电有效；
  主机用它派生会话密钥（PBKDF2/HKDF），保证"串口旁的旁观者"拿不到明文 key；
- **信任边界**：配网走 USB 串口，默认操作者物理接触设备——这一点如实写；
- 写入成功后清临时码、退出未配置模式、要求重启生效。

### 5.4 主机侧钥匙管理

- 新工具 `scripts/provision-device.cjs`（`npm run provision -- --port COM11 --label ws63-A`）：
  生成 key → 走配网协议 → 写入成功后存进设备表；
- 设备表文件：`data/devices.json`（**不入库**，`.gitignore`），权限 600；
  Windows 上优先 DPAPI 加密（`ProtectedData`），退路是明文 + 目录 ACL；
- 控制台/CLI 选择设备：`--device-key <file>` 或 `SAFE_OFFICE_DEVICE_KEYS`；
- **演示密钥只保留给测试**：必须显式 `--demo-key`；生产模式（`SAFE_OFFICE_PRODUCTION=1`）
  下拒绝演示密钥并直接报错。

### 5.5 协议影响

SFC1 帧格式**不变**（密钥只是 HMAC 的输入）。新增的是配网帧类型（0x10/0x11），
需要同时改 `ws63/protocol.c` 与 Node 侧编解码，并补双向测试。

## 7. 测试计划

- **单测**：密钥记录编解码/tag 校验；未配置模式拒绝普通 CHALLENGE；生产模式拒绝 demo key；
  两台设备不同 key 交叉验签必须失败（一机一钥的核心断言）。
- **真板**：配网（正确码/错误码/重复配网）、断电重启后 key 仍在、配网后旧 demo-key 帧被拒。
- **回归**：现有 502 项测试默认仍用 demo key（显式参数），不受影响。

## 8. 风险与开放问题

1. **eFuse 地址分配未知**：第二阶段必须先拿到厂商文档；写错可能变砖。
2. **配网通道信任**：USB 串口 = 物理接触；临时码只能防旁观，不防接触者。
3. **不可轮换**：NV 覆盖即可轮换；eFuse 写死无法轮换，只能换板。
4. **NV 被擦除**：设备回到未配置模式，需要现场重新配网（可作为恢复流程）。
5. **生产模式开关**：`SAFE_OFFICE_PRODUCTION=1` 会不会影响现有 E2E/演示？需要确认默认值。
6. **多设备主机**：设备表 + 按 device_id 选 key；控制台当前只支持单设备，是否要扩多设备 UI？
