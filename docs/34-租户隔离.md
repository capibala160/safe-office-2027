# 租户隔离（v0.33）

> 2026-10-31 第三块软件收尾。目标：把「操作发起人」从审计字段升级为真正的数据边界——
> 普通员工只看到自己的资料/操作/运行历史；审批与治理角色按职责跨租户。
> 租户 = 登录用户名（不是组织/企业）；仍不是生产级多租户。

## 1. 隔离模型

| 角色 | 文档 | 操作/审批队列 | 运行历史 | 审计/治理明细 |
|---|---|---|---|---|
| 员工 / 实习生 / 访客 | 共享样例 + 自己导入 | 自己发起的 | 自己的 | 无（审计页 403；治理页只给聚合分） |
| 设备助手 | 共享样例 + 自己导入 | **全部冻结操作（审批队列）** | 自己的 | 无 |
| 管理员 / 审计员 | 全部 | 全部 | 全部 | 全部 |

未启用登录（`auth=null`）时 `actor=null`，保持旧的单工作区行为，便于本地演示/测试。

## 2. 文档隔离

- `documents` 表新增 `owner`；旧库启动自动补列，旧资料 `owner=''` 视为共享（升级后不会突然消失）。
- 导入 ID 改为按 `owner + 内容哈希` 派生：同一份文件被不同用户导入得到不同 ID，互不覆盖。
- `POST /api/documents/import` 的角色从「仅管理员」放宽到「员工/管理员」；`owner` 取登录用户。
- 三处强制：
  1. **令牌签发**：其他租户的文档 ID 从 `token.documentIds` 移除，并记入 `deniedDocs`；规划上下文不会读到别人的正文。
  2. **列表/详情**：`listDocuments/getDocument` 按 owner 过滤；访问别人的导入资料返回 404。
  3. **知识库**：readDoc/图片识别/转写/正式稿写入 `runtime.knowledge` 时带 `owner`；`shareScreen`/闸5 的机密检查只看本租户条目，避免 A 读过机密导致 B 被连带拦截。
- UI 文件列表新增「归属」列（`共享` / 用户名）。

## 3. 操作与运行历史

- 操作记录已有 `createdBy`（v0.31）；v0.33 在服务层统一过滤：
  - `listOperations` / `getOperation` / 正文导出 / 版本历史 / 附件下载 / 驳回 / 发起挑战 / 校验 / 发送：非本人且无跨租户角色 → 404（不暴露存在性）。
  - 设备助手可以读操作列表与详情（审批队列），但不能读文档正文、审计、运行历史。
- `listRuns/getRun/cancelRun`：员工只看自己的运行；管理员/审计员全部。
- `state.counts`（文档/操作/待确认/运行）按租户计算；设备助手看到全部待审批数。
- 审计：`AuditLog.append` 在命令执行期间自动写入 `actor`，并纳入哈希；旧条目无 `actor`，哈希兼容。`state.audit.recent`、日历代理事件、治理页审计/风险明细对非管理员/审计员返回空。
- 风险分/冻结状态仍是全局聚合（一个租户的异常会抬高全局风险分）；这是有意的系统级保护，不是隔离缺陷。

## 4. 明确的边界

- **手机确认端**：配对码是服务级、不是租户级；配对后的手机会看到当前待确认挑战。按「一台可信审批设备」设计，不能防止它看到其他租户的待确认操作。
- **操作详情**：设备助手/管理员/审计员可看操作正文与附件元数据；这是审批职责所需。
- **审计链**：仍是全局单链，不是每租户一条链；隔离的是读取面，不是链结构。
- **联系人/日历种子**：共享演示数据，不隔离。
- 不是数据库行级安全（RLS），服务层过滤依赖每个入口都传 `actor/role`；新增入口必须复用 `userContext(req)`。
