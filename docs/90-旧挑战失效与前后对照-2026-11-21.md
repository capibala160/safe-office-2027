# 旧挑战失效 → 收件人/附件对照 → 新版本确认 → 回执（真板，2026-11-21）

> 补上 UI/服务层回归与真板之间的最后一环：
> **旧挑战在 B 板上仍显示、用户仍按了 KEY2、板端仍回 APPROVED，但 PC 以“挑战已作废”拒绝，不执行；**
> 换收件人 + 同名同大小附件（内容哈希不同）后重新确认，才产生执行与回执。
>
> 证据：`ws63/logs/supersede-receipt-20261121/evidence.json` + `summary.md`。
> 脚本：`npm run supersede:check -- --port COM11 --device ws63-B`（6 项纯逻辑单测）。

## 1. 为什么单独做这一轮

已有验证：

- **浏览器 E2E**：修改收件人与附件 → 旧草稿撤销 → 旧挑战过期 → 新版本确认 → 回执/回放（UI 全流程）；
- **服务层回归**：撤销后旧挑战不能批准；新收件人绑定独立操作、独立哈希。

但两者都没有证明**真板上的旧挑战被 PC 拒绝**。本轮用双板真机把这条补齐：

| 层 | 已验证内容 |
|---|---|
| UI | 对照界面、按钮流程、刷新后仍能对照 |
| 服务 | 旧挑战状态为 expired、旧操作 rejected、新挑战 targetHash = 新 operationHash |
| **真板（本轮）** | **旧挑战帧在 B 板显示并回 APPROVED；PC 仍拒绝且不执行；新版本再按键才执行** |

## 2. 场景与结果（9/9 PASS）

| 步骤 | 实际结果 |
|---|---|
| 1. 冻结旧外发（`partner@partner-example.com`，附件 `agenda.txt` 21B） | 旧操作 `24e75912…`，旧挑战 `ce0d977d…` |
| 2. 旧挑战帧发到 B 板，用户等 5 秒后按 KEY2 | 板端回 DECISION；PC 返回 **`CONFLICT 挑战已作废，请检查当前任务状态`** |
| 3. PC 撤销旧草稿 | `voidedChallenges=1`；旧挑战 `expired`；旧操作 `rejected` |
| 4. 新建新版本（`review@partner-example.com` + 同名同大小新附件） | 新操作 `6d09515d…`，新挑战 `15875dbc…` |
| 5. 新挑战发到 B 板，短按 KEY2 | `ok=true outcome=approved code=OK` |
| 6. 执行与回执 | 操作 `executed`；outbox `sent`；`confirmationId=ws63-5c1331ed…`；`messageId=fake-message-1-1` |
| 7. 审计链 | `verify()=true`，29 条；「操作拒绝」记录 `voidedChallenges=1` |

**断言明细**：旧挑战失效、旧挑战不能被批准、收件人变化、同名附件替换、新目标哈希匹配、
新版本真板批准、执行 + outbox、回执存在、审计链通过 —— **全部 PASS**。

## 4. 演示口径（答辩可用）

> 设备端看到的是旧版本，用户也按了批准；但控制台在收到决定前已经撤销了旧草稿。
> 因此板端的 APPROVED **不被接受**——旧挑战作废、操作不执行、没有回执。
> 换成新收件人和新附件后重新发起挑战，板端再按一次，才产生新的确认号与回执。

**不能写成**：板端按键 = 一定执行；锁舌动作；真实邮件已发出（本轮用 FakeMailer）。

## 5. 运行记录与边界

- 第一次运行：第二轮按键被板端判为**长按取消**（`DECISION`），新版本未执行；
  这是操作节奏问题，不是机制失败。重跑时第二轮轻点即通过。
- `messageId=fake-message-1-1` 来自 **FakeMailer**，本轮不接真实 SMTP；回执编号与 outbox 状态是真实服务链路产物。
- 未录视频；B 板旧/新摘要的 OLED 画面没有截图归档（操作者目视）。后续视频按 docs/89 §6 拍。
- 单场景、单轮；重复运行只说明稳定性，不增加独立样本量。

## 6. 复现

```bash
cd prototype
# 先识别端口（每次插拔后）：A=COM11、B=COM12

npm run supersede:check -- --port COM11 --device ws63-B

```
