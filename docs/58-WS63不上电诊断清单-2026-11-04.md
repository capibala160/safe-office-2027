## 1. 两条硬结论（先把范围砍掉一半）

电源树（按原理图逐页读出）：

```
USB VBUS ─F1(保险丝)─D1(肖特基)─S1(开关)─ VIN_5V
                                            ├─ U12 SY8089 buck ─→ VIN_3V3
                                            │                      ├─ WS63 核心板 VBAT
                                            │                      ├─ CH340N VCC/V3（USB 转串口）
                                            │                      └─ Q3(P-MOS) ─→ 3V3
                                            └─ Q1(P-MOS) ─→ 5V（排针）

3V3 / 5V 由 Q1、Q3 开关；两管栅极被 Q4 拉低才导通；
Q4 栅极经 R5 47k + C7 1µF 由 REST 延时约 30ms 拉起（01 页）。
KEY1 把 REST 直接短路到 GND（04 页）。REST 同时是核心板的复位脚。
```

- **结论 1：CH340N 的 VCC 与 V3 都接在 VIN_3V3 上**（03 页 U9 第 5/8 脚）。
  所以**设备管理器里能看到 CH340 的 COM 口 ⇒ S1 在开、USB 数据线通、F1/D1/U12 这一段 5V→3.3V 正常**。COM 口出现不能证明核心板活着，但能证明它的供电上游活着。
- **结论 2：电源指示灯 LED3 的阳极接 3V3**（04 页 LED3 + R20 1kΩ 到 GND）。
  所以**LED3 亮 ⇔ Q3 之后的 3V3 轨已使能**；OLED、传感器、排针 3V3 也都在这条轨上。

一块板只剩四种状态，看**一个灯 + 一个端口**就能定位到段：

| COM 口 | LED3（电源灯） | 含义 | 去哪 |
|---|---|---|---|
| 有 | 亮 | VIN_3V3 与 3V3 都正常；核心板有电但不启动 | §3-A |
| 有 | 灭 | VIN_3V3 正常，3V3 没使能（REST→Q4→Q3 段） | §3-B |
| 无 | 灭 | VIN_3V3 都没有（F1/S1/线/USB 段） | §3-C |
| 无 | 亮 | 图纸上矛盾（LED3 由 3V3 供电）；实际含义是 CH340 或 USB 数据线坏 | §3-D |

## 2. 本次已确认的现场事实（2026-11-04）

- **电源灯 LED3 亮**（[docs/57](57-M3板端SFC1与串口CLI-2026-11-04.md) §5 记录）⇒ 由结论 2：**3V3 轨已使能**，REST 已被拉高，Q4/Q3 这段正常
- `npm run serial:probe -- --list`：**COM11 存在**，`manufacturer=wch.cn`，`VID:PID=1A86:7523` → CH340N 已枚举 ⇒ 由结论 1：**VIN_3V3 正常**
- 115200 / 921600 各监听 5 秒：**0 字节**（退出码 3）
- 扩到 10 档波特率（9600 / 19200 / 38400 / 57600 / 115200 / 230400 / 460800 / 921600 / 74880 / 1500000）各监听 3 秒：**全部 0 字节** ⇒ 不是波特率不匹配，是根本没有波形

**落点：§3-A（COM 有 + LED3 亮）。** 两段电源都正常、复位也已释放，核心板却不启动。
剩下的可能只有三类：核心板本身（VBAT/晶振/模组损坏）、启动配置脚在上电时被拉高（KEY2 卡住或排针上挂了外设）、
或 UART0→CH340 这一段断线（但 OLED 黑屏 + 运行灯不闪说明不只是串口断线）。

> **本节是 11-04 白天的推断；当晚已收口，结论见 §9——真正的原因是「被动监听抓不到只在启动瞬间打印的固件」+ 第一块板本身异常。**

## 3. 分支流程

### 3-A COM 有 + LED3 亮（**当前所在分支**：核心板不启动）

0. **先做减法**：拔掉排针上所有杜邦线 / SPI LCD，只留 USB；上电时手不要碰 KEY2。
   03 页注明 IO1/IO3/IO4/IO6/IO9/IO11 是硬件配置脚、**上电必须为低**；KEY2 就是 IO3（板上有 R15 10k 下拉），
   按键卡住或外设把配置脚拉高，都会改掉启动模式。
1. 量 **核心板 VBAT**（核心板旁的 C22 正极 / U7 第 7 脚）：应 3.2~3.3V。0V ⇒ 模组供电脚虚焊/断线。
2. 量 **REST**（KEY1 非地脚）：应 3.2~3.3V；按住 KEY1 应 0V，松开回 3.3V。
   LED3 已经亮，REST 理论上不会常 0V；若量到 0V，先确认是不是量到了 GND 那脚。
3. 做 **§4 串口回环**。通过 ⇒ CH340 与线材无罪，问题在 SoC 侧；不通过 ⇒ 先换线/换口/换电脑。
4. **按 KEY1 两秒再松开**，同时盯串口和 OLED：
   - 有 `boot.` / `Flash Init` 之类输出 ⇒ 模组活着，是应用镜像的问题（重新烧录即可）；
   - **完全无反应** ⇒ 模组没执行。注意：这**不是固件问题**——引导程序在应用之前就会打印 `boot.`，
     0 字节说明连引导都没跑起来。
5. 结论：1~4 都正常仍 0 字节 ⇒ 核心板/晶振损坏，按 §8 报修/换板。

### 3-B COM 有 + LED3 灭（3V3 没使能；本轮已排除，留作下次备查）

1. **先量 REST（不按键）**：
   - **≈0V ⇒ KEY1 卡住 / C35 短路 / 核心板没释放复位**。这是最省事的解释，也最能解释「两块板同时坏」。
   - 目视 KEY1 是否被外壳、收纳海绵、按键帽压住（复位键是高的直插轻触键，收纳时最容易被压）。
   - 万用表通断档量 KEY1 两脚：**未按应不通**，按下才通。
2. REST ≈3.3V 但 **C7 正极（Q4 栅极）≈0V** ⇒ R5/C7/D2 这条延时链路开路（受潮/焊接，少见）。
3. Q4 栅极 ≈3.3V 但 **Q3 栅极仍 3.3V** ⇒ Q4 或 Q3 损坏。
4. **不建议自行短接栅极改线**：板上是 0402/0603 封装，短接错了会把 3V3 直接怼到 5V。测完直接送修。

### 3-C COM 无 + LED3 灭

1. 换 USB 口、换**数据线**、换一台电脑（三样分开换，别一起换）。
2. 量 **VIN_5V**（D1 阴极 / C1 正极）：0V ⇒ F1 熔断（USB 过流）或 S1 坏。
3. 量 **VIN_3V3**（C44 正极 / 核心板 VBAT）：0V ⇒ U12 损坏。
4. S1 拨到位：关机档会把负载短到地，半到位时最坑。

### 3-D COM 无 + LED3 亮

- 驱动/线材/CH340 本身。设备管理器看有没有黄色感叹号；换线换口再试。
- 3V3 有电时**不要带电插拔排针**。

## 4. 串口回环（不需要示波器，单独判定 USB 转串口链路）

原理：SW1=1 时 USB 的 TX/RX 直连排针 **UTX/URX**（03 页 U10 CH440E 通道 S2）；把这两针短接，PC 发什么就该原样收到什么，与核心板无关。

1. **断电**，SW1 拨到 **1**。
2. 用一根杜邦线短接底部横排针相邻的 **UTX ↔ URX**。
   底部排针从右往左：`5V / UTX / URX / IO18 / IO17 / GND / GND / IO16 / IO15 / IO14 / IO13 / IO12 / IO11 / IO10`——**UTX/URX 紧挨着 5V，插线别错位**。
3. 上电，执行：

   ```bash
   cd prototype
   npm run serial:probe -- --port COM11 --loopback
   ```

4. 判读：
   - **通过** ⇒ USB 线、CH340、驱动全好，问题在 SoC 侧。
   - **不通过** ⇒ 换线/换口/换电脑再试；仍不通过 ⇒ CH340 或 USB 座坏。
5. 测完：**SW1 拨回 0**，拔掉短接线。

> 只短接 UTX↔URX（3.3V 逻辑，短接安全）。**绝不要短接 3V3/5V 与相邻针。**

## 7. 判定收敛与共因

- **可修（不换件）**：线材/驱动/SW1 挡位/KEY1 卡滞。
- **需送修/换板**：REST 正常、3V3 正常、回环通过、串口仍 0 字节 ⇒ 核心板。
- **两块板同时出问题，优先怀疑共因**：同一根线、同一个 USB 口、同一台电脑、收纳时 KEY1/KEY2 被压、同一次带电插拔。先把「按键是否被压住」和「换线换口」排掉，再下「两块都坏了」的结论。

## 9. 2026-11-04 晚收口：结论与教训

**结论：不是电源问题，也不是"两块板都坏了"。**

- 电源两段（VIN_3V3 / 3V3）由 CH340 枚举 + 电源灯亮已经证明正常，§3-A 的电源分支全部排除
- **真正的坑是观测方法**：M3 固件和厂商 SDK 示例都**只在启动瞬间打印**，启动完成后串口是安静的。
  被动监听（不复位）必然 0 字节——10 档波特率全 0 也是这样来的
- 正确姿势（写进日常流程）：
  1. 先起监听：`npm run serial:probe -- --port COM11 --baud 115200 --seconds 120 --watch`
  2. **看到 `[打开]` 那行之后**再按 KEY1，或 S1 断电重上电
  3. 日志里出现 `boot.` 才算真的抓到了启动
- **换板后一次握手成功、烧录通过**；第一块板**芯片被锁**（用户说明）——这直接解释了它为什么
  `hsflash` 握手失败、上电无输出。**锁定方式与是否可逆未核实**：先向厂商确认能否解锁/返修，
  再决定当备件还是报修。它不是电源/核心板故障，本清单的电源分支对它无效
- 工具坑：后台监听被 `TaskStop` 停掉后，Windows 上 node 子进程可能残留并继续占用 COM 口，
  下一次打开报 `Access denied`。处理：

  ```powershell
  Get-CimInstance Win32_Process | Where-Object { $_.Name -eq "node.exe" -and $_.CommandLine -like "*serial-probe*" }
  Stop-Process -Id <pid> -Force
  ```

- 复测第一块板：按 §3-A 的"先做减法"→ 量 VBAT/REST → §4 回环；仍无输出再走 §8 报修

**M3 真机结果**见 [docs/57](57-M3板端SFC1与串口CLI-2026-11-04.md) §6
