# 退信处理（v0.35）

> v0.10 起发送闭环管到"SMTP 接了没有"（sent / failed / unknown），但**对方服务器事后退信**
> 系统完全不知道：邮件页仍显示"已发送"，收件人其实没收到。
> 本轮补上发出去之后的那半程：解析 DSN 退信报告 → 按 Message-ID 回填发件记录 → 进审计。

## 1. 做了什么

**解析（`src/dsn.cjs`，零依赖）**

- 识别 `multipart/report; report-type=delivery-status`（RFC 3464），也兼容没有 MIME 结构的简版退信。
- 逐个收件人取出：`Final-Recipient`、`Action`（failed/delayed）、`Status`（5.x/4.x）、
  `Diagnostic-Code`、`Remote-MTA`。
- 原始 `Message-ID`：优先取内嵌 `message/rfc822` 的原信头，其次 `Original-Message-ID` / `X-Original-Message-ID`。
- Message-ID 统一去尖括号、转小写后比较。

**状态机（`src/store.cjs` / `src/fulfillment.cjs`）**

- 新增 outbox 状态 `bounced`，唯一入口是 `sent → bounced`（重复登记幂等）。
- **`unknown` 不接受自动回填**：客户端超时拿不到服务端 Message-ID，无法可靠匹配；
  必须先人工核对成 `sent`，退信才能落。
- `failed` / 已 `bounced` 的记录不接受退信，如实报告跳过原因。
- 操作记录保持 `executed`（发送动作确实执行过），投递失败由 outbox 状态表达；
  若操作还停在 `executing`（unknown 核对后场景），登记退信时一并落 `executed` 并写入 `result.bounced`。
- **绝不自动重发**：退信后要再发必须新建操作、重新冻结、重新确认。

**接口与界面**

- `POST /api/bounce`（管理员/审计员），body `{ eml }`，返回逐条结果与汇总。
- 治理页新增「退信处理」卡片：粘贴 `.eml` 或选文件 → 解析并回填，显示
  `回填 / 重复 / 跳过 / 未匹配 / 忽略` 计数与每条明细。
- 邮件记录列表显示退信数；outbox 状态标签新增「退信」。
- 每次导入都写审计（`退信` / `退信未回填`，含操作者），审计链照常参与哈希。

```bash
npm test    # 336 项：335 通过 + 1 跳过（ClamAV 未配置时）
```

`test/dsn.test.cjs` 11 项：

- Gmail 风格退信：收件人 / 5.1.1 / Diagnostic / 内嵌原信 Message-ID。
- 多收件人：failed + delayed 分列，共享同一 Message-ID。
- 无 MIME 简版退信（`Original-Message-ID` 回退，大小写归一化）。
- 普通邮件不识别为退信。
- 幂等：同一封退信导入两次，第二次只报 `duplicate`。
- `unknown` 拒绝自动回填 → 人工核对为 sent → 退信落 bounced。

## 3. 边界（别把它说大）

- **没有做 IMAP/POP3 自动收信**：退信 `.eml` 目前由人工从邮箱导出后粘贴/上传。
  自动拉取需要邮箱授权与轮询，属于下一轮。
- 只按 `Message-ID` 精确匹配，不做"按收件人+时间"的模糊匹配（宁可漏，不猜）。
- 延迟通知（`Action: delayed`）只入审计，不改状态：它不代表最终失败。
- 退信只影响本系统账目，不改变对方邮件系统的任何状态；也不证明对方没读过此前其它邮件。
- 解析器覆盖常见 MTA（Gmail/QQ/Exchange）格式，但 MIME 变体很多，遇到解析不了的原文会明确 400，而不是猜。
