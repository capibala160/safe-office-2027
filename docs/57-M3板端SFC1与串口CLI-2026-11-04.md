## 1. 板端固件（M3）

### 文件

| 文件 | 作用 |
|---|---|
| `ws63/firmware/board-confirm/board_confirm_m3.c` | 主任务：UART 收帧 → OLED 显示 → KEY2 决策 → 回 DECISION |
| `ws63/firmware/board-confirm/sfc1_hmac.c/h` | mbedTLS 3.6 HMAC-SHA256 + device_id 派生 |
| `ws63/protocol.c/h` | 帧编解码/校验（与 PC 测试共用同一份源码） |
| `ws63/firmware/build-m3.cjs` | 同步进 SDK + 清理旧对象 + 调 `build.py` |

### 行为

- UART0，**115200 8N1**，与控制台共用；PC 侧解析器按 `SFC1` 魔数重同步，文本日志不干扰
- 收到 CHALLENGE：验 MAC → 查重放窗口 → 检查是否有未过期待确认 → 存 pending 并显示
- OLED：`WS63 CONFIRM` / 动作（SEND EXT / DELETE / PRINT / DEVICE）/ 摘要 / `OK:SHORT NO:LONG <TTL>s`
- KEY2 短按 = 批准（decision=1），长按 ≥600ms = 取消（decision=0）；与 M2 相同的候选脚+去抖
- 回 DECISION：HMAC-SHA256，`device_id` 与 PC 同域派生，`decided_at` 用本地毫秒时钟
- 超时：按 `expires_at - issued_at` 换算本地 deadline（板上无 RTC），到点清 pending 并消费 nonce
- 重放：8 条 nonce 环形窗口；过期 pending 的 nonce 也会被消费

### 固定值（演示）

- PSK：`DEMO_KEY` = 32 × `0x42`（与 CLI `--demo-key` 对应）
- 设备名：`ws63-A`；`device_id = SHA-256("safe-office/ws63/device-id/v1\0" + "ws63-A")[0..8]`
- ⚠️ 真实部署必须改为每台设备独立密钥 + 安全存储；当前仅用于联调

### 编译

```bash
node ws63/firmware/build-m3.cjs            # 只同步源码进 SDK
node ws63/firmware/build-m3.cjs --build    # 同步 + 编译（约 18s，增量）
# 或在 prototype/ 下：npm run ws63:build
```

产物：`D:/fbb_ws63/src/output/ws63/fwpkg/ws63-liteos-app/ws63-liteos-app_all.fwpkg`

构建脚本做的事：

1. 把仓库源码同步到 `src/application/samples/base_03_ssd1306/`（含 `protocol.c/h`）
2. 删除 SDK 里的旧样例源 `base_ssd1306_demo.c` 与旧 `libsamples.a`/目标目录
3. 补 PATH（工具链 / ninja / gn / ccache）后调 `build.py ws63-liteos-app`

> 踩坑记录：SDK 的 `build.py` 需要 `ccache` 与 `ninja` 在 PATH，HiSpark Studio 会自动注入；
> 手跑必须自己加 `D:/HiSparkToolchain/tools/cfbb/thirdparty/ccache`，否则报
> `CreateProcess failed: The system cannot find the file specified`。

## 2. PC 侧串口确认 CLI

```bash
cd prototype
node serial-confirm.cjs --port COM12 --demo-key --to partner@example.com --subject "Quarterly report"
node serial-confirm.cjs --port COM12 --key <64位hex> --device ws63-A --action printDoc --to "HP LaserJet"
```

| 选项 | 说明 |
|---|---|
| `--port` | 必填，CH340 的 COM 号（以设备管理器为准，可能变） |
| `--to` / `--subject` / `--body` | 操作内容；摘要进 CHALLENGE，OLED 显示 |
| `--action` | `sendExternalEmail`(1) / `deleteDoc`(2) / `printDoc`(3) / `deviceControl`(4) |
| `--device` | 期望设备名，默认 `ws63-A` |
| `--ttl` / `--timeout` | 确认 TTL（默认 30s）/ 串口回复超时（默认 15s） |
| `--demo-key` | 使用演示密钥（必须显式） |
| `--key` / `SAFE_OFFICE_SFC1_KEY` | 真实 32 字节密钥（64 位十六进制） |
| `--json` | 机器可读输出 |

退出码：`0` 批准；`1` 其它失败（TIMEOUT/MAC/DEVICE/DECISION…）。

> ⚠️ **实测不一致（2026-11-04 晚）**：取消路径实际返回 `1` +
> `{"ok":false,"code":"DECISION","message":"用户取消"}`，而不是本文原先写的 `2`。
> 原因：`NearfieldConfirmer.acceptDecision` 对 decision=0 抛 `DECISION`（`cancelled:true`），
> CLI 的 catch 统一返回 1，导致 `decision===1 ? 0 : 2` 的 `2` 分支不可达。
> 取消的**语义**是对的（消费 nonce、不产生批准、不执行）。
> **2026-11-04 拍板：保持退出码 1**，不引入 2——调用方用 `code:"DECISION"` 区分取消即可。
> 死分支 `decision===1 ? 0 : 2` 已删成 `return 0`。

流程与虚拟设备完全一致：`sealOperation` 冻结 → `NearfieldConfirmer.beginChallenge` →
`SerialTransport.send` → 板端按键 → `acceptDecision` 验 MAC/绑定/nonce。

## 4. 边界

- **固件未上机验证**：编译通过 ≠ 真机通过；UART0 与控制台共用、RX 回调注册、OLED 显示、
  mbedTLS 链接都只经过编译验证
- 演示 PSK 编译进镜像；无安全存储、无密钥轮换
- 板上无 RTC：TTL 用本地时钟换算，设备重启后 pending 丢失（重启后旧挑战不能复用，nonce 窗口也清空——
  这是已知边界，真机验收时要单独测"确认中拔电"）
- OLED 字体不含中文：摘要含中文会显示 `?`；演示建议用 ASCII 主题
- 不证明距离/身份/防中继

### 6.5 异常项上板（进行中）

| 异常 | 方法 | 结果 |
|---|---|---|
| **错设备 DEVICE** | `--device ws63-B`，板端照常短按 KEY2 | ✅ `{"ok":false,"code":"DEVICE","message":"设备 ID 与可信配对配置不符"}`，退出码 1 |
| **改帧 MAC** | `npm run sfc1:neg -- --case mac`（只翻 MAC 末字节） | ✅ 板端 `SFC1 challenge rejected: MAC` |
| **未决重复 BUSY** | `--case busy`（连发同一帧） | ✅ `rejected: BUSY`，到期后自动清 pending |
| **过期 EXPIRED** | `--case expire`（挑战帧 TTL=2s） | ✅ 板端 `SFC1 pending expired` |
| **重放 REPLAY** | `--case replay`（过期消费 nonce 后重发同一帧） | ✅ 板端 `rejected: REPLAY` |
| **PC 侧超时** | `--timeout 6000`，全程不按键 | ✅ `{"ok":false,"code":"TIMEOUT","message":"确认端无响应（超时）"}`，退出码 1；板端 pending 需按键或断电清除 |

> 负向工具 `prototype/scripts/sfc1-negative.cjs`（`npm run sfc1:neg`）直接构造 SFC1 帧，
> **全程不需要按 KEY2**：挑战帧自带 2~3 秒 TTL，板端到期会消费 nonce 并清 pending，
> 因此不会像 `serial-confirm` 那样把板子占住 600 秒。

### 6.7 M1 掉电保存（2026-11-04 晚）

**问题**：nonce 窗口原来只在 RAM，重启即清空——同一帧在断电重上电后又能被接受。

**做法**（`ws63/firmware/board-confirm/sfc1_nv.c/h`）：

- 把已消费 nonce 的 8 条环形窗口写进 NV（key `0x0F01`，160 字节）：
  `magic "SFC1NV1" | version | count | seq | nonces[8][16] | HMAC-SHA256(psk, 前144B) 前16B`
- 启动时 `sfc1_nv_load()`：校验 magic/version/HMAC，恢复窗口并设置写指针；
  无记录/损坏按空窗口启动并打印，不阻断确认流程
- 每次 `mark_used()`（按键决定或过期消费）后 `sfc1_nv_save()`；写失败只打印 `SFC1 NV: save failed`

**真机验证**：

1. 烧录新固件，启动日志出现 `SFC1 NV: no record` → `SFC1 NV: empty replay window`
2. `npm run sfc1:neg -- --case persist-arm`：挑战接受 → 2s 过期 → 帧存到临时文件
3. **S1 断电重上电**（清 RAM）
4. `npm run sfc1:neg -- --case persist-check`：重发同一帧 → ✅ `SFC1 challenge rejected: REPLAY`

**边界**：PSK 仍编译在镜像里；NV 被擦除/损坏时按空窗口启动（fail-open，可被物理擦 NV 绕过）；
写 seq 只用于调试，不做回滚检测；NV 写发生在 UART/按键任务上下文，写失败不影响本次确认。
