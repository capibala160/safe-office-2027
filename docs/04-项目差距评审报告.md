## 结论

当前仓库已经形成一个可复现的 Node.js 安全机制原型：`npm test` 实际通过 62 项测试，覆盖五道闸、工具沙箱、策略、审计链、风险冻结、模型边界和治理报告。它可以支撑“机制演示”和方案答辩，但还不能作为“已在 OpenHarmony 6.0.0.1 Release 上完成的可运行办公系统”提交。主要缺口集中在真实平台/真实工具验收，以及若干可被绕过的授权边界。

## 高优先级发现

### F-01 内部邮件动作未校验收件域名

**证据**：`prototype/src/guard.cjs:64-76` 仅为 `sendExternalEmail` 校验域名；`prototype/src/runtime.cjs:297-301` 对 `sendInternalEmail` 直接写入 outbox。复现中，员工持有 `sendInternalEmail` 令牌时，可以把邮件发送到 `attacker@evil.example`，并产生 outbox 副作用。

**影响**：攻击者或被污染的模型可把“内部邮件”工具当作任意网络外发通道，绕过外部域名白名单、外发确认和数据边界。

**建议**：把内部邮件限制为受信任企业域名/组织目录中的精确地址；内部与外部路由在工具适配器层再次校验，不能只依赖规划器。

### F-02 删除文件未检查目标资源授权

**证据**：`prototype/src/runtime.cjs:113-121` 的资源令牌检查只覆盖读取、识别、转写，以及带 `docId` 的动作；`deleteDoc` 使用 `id`，因此没有检查 `token.documentIds`。复现中，令牌没有任何授权文档仍可删除已读入的 `M2`。

**影响**：任何获得删除工具的任务令牌都可能删除未授权资源，违反最小权限和文件访问分级要求。

**建议**：把“所有文档资源动作”统一映射到资源 ID 检查，包括 `deleteDoc`、`printDoc`、`summarize` 及生成稿来源；删除前还应检查文档版本/状态。

### F-03 令牌状态未参与模型上下文装配

**证据**：`prototype/src/runtime.cjs:75-77` 只按 `token.documentIds` 和角色策略筛选文档，没有检查令牌缺失、撤销或过期。一个已撤销令牌仍可把授权文档正文送入规划器上下文；`checkToolCall` 的令牌检查发生在模型规划之后。

**影响**：撤销或过期后的任务仍可能把敏感正文暴露给本地/云模型，也会产生不一致的审计记录。

**建议**：在 `runCommand` 开始处验证令牌生命周期和任务主体；上下文装配与工具执行共用同一个授权快照，失败时 fail-closed，不调用模型。

### F-04 未知密级被当作可内网发送

**证据**：`prototype/src/guard.cjs:96-111` 仅拒绝 `机密`，其它值包括未知值都会进入内网发送分支。未知密级不应自动获得“内部可原样发送”的待遇。

**影响**：数据分类失败时可能发生未审查的信息外发，破坏“未知即拒绝”的安全默认值。

**建议**：显式枚举 `公开/内部/机密`；未知或缺失密级统一阻断外发、上传、打印和共享，并记录待人工分类事件。

## 中优先级发现

### F-05 云模型请求会脱敏用户目标地址 ✅ v0.7 已整改

> **整改（v0.7）**：云侧指令中地址/链接 → `[目标N]` 占位符，真实值留端侧；模型计划引用占位符 → 端侧回填真值 → 授权校验仍锚定用户指令原文。未登记占位符/编造地址一律移除。

`prototype/src/model-boundary.cjs:12` 对云侧 command 整体调用 `redact`，因此用户明确输入的收件地址会变成脱敏占位符。当前 MockLLM 不受影响，但真实 HttpLLM 可能无法生成可执行的精确目标，或在模型返回后与原指令无法匹配。应将“用于授权匹配的结构化目标”与“送模型的脱敏文本”分离。

### F-06 规划/模型异常没有统一安全失败结果 ✅ v0.7 已整改

> **整改（v0.7）**：模型故障归一为固定类别（超时/网络/HTTP/非法JSON/空响应/未配置/边界拒绝）；规划失败 → 零执行 + 审计 + 用户可见；执行中故障 → 任务中止（其后步骤不执行）；`taskId` 幂等键防重试双发；任务结束自动吊销令牌。

`prototype/src/runtime.cjs:74-79` 及 `prototype/src/planner.cjs:104-106` 的模型异常向上抛出；审计只留下“用户指令/数据流向”，没有标准化的“规划失败/未执行”事件和用户可见结果。真实网络超时、非法 JSON、空响应、重复执行需要统一 fail-closed、审计和幂等处理。

### F-07 确认与审计仍是主机模拟

`prototype/src/confirmation.cjs:20-23` 的 `simulateResponse` 由同一进程生成，`prototype/src/guard.cjs:124-130` 的近场状态是布尔参数。文档已正确标注这不是身份、距离或防中继证明；在 OpenHarmony/WS63 上板前不能宣称真实近场确认已完成。

### F-08 审计检查点未形成独立信任根

`prototype/src/governance.cjs:75-83` 将检查点与审计文件一起保存。文档已说明这一限制，但提交材料应明确：跨重启防篡改仍需 HUKS 签名或独立受保护存储，否则只能证明“当前内存链未被改动”。

## 优先级路线

1. **P0 修复授权边界**：先补 F-01 至 F-04 的代码与回归测试；这些问题会直接削弱答辩中的“安全调用控制”结论。
2. **P1 做最小真实闭环**：在隔离测试邮箱和虚构文档上接入 HttpLLM、邮件适配器、持久化审计；验证超时、非法 JSON、重试、幂等、目标变化和断网恢复。
3. **P1 上 OpenHarmony**：取得确切的 6.0.0.1 Release 镜像/SDK 证据，完成 hdc、ArkTS 空应用、文件/网络/密码学/权限接口验证。
4. **P2 接入信任根**：HUKS 审计签名、重启验签、密钥不可导出；再做 WS63 双节点 SLE 握手、错误 MAC、重放、超时和断线测试。
5. **P3 形成提交物**：方案介绍文档、上板版机制说明、设备测试记录、可复现攻击样例、演示视频和端侧治理界面。当前没有 Demo 视频，也没有可证明 OpenHarmony 实机运行的材料。
