# 运行时闸4 接真板：设计稿（2026-11-04）

> **只设计，不改代码。** 目标是让 `runtime.cjs` 的闸4（高危二次确认）从"进程内模拟"
> 变成"必须由 WS63 真板物理按键产生的 SFC1 DECISION"。
> 现状与相关实现：[docs/11](11-WS63确认适配器.md)、[docs/57](57-M3板端SFC1与串口CLI-2026-11-04.md)。
>
> **进度（2026-11-04）**：
> - **第 1 批 ✅**：`runtime.cjs` 增加 `humanConfirm` 接缝，默认仍走 `requestHumanConfirm`；
>   3 项测试覆盖"放行/拒绝/抛错"，其中"确认端拒绝时即使 `nearfieldOnline=true` 也不执行"已由测试钉住。
> - **第 2 批 ✅**：`src/board-human-confirm.cjs`（SFC1 挑战/校验）+ 控制台开关
>   `SAFE_OFFICE_GATE4_NEARFIELD=1`；9 项单测 + 1 项控制台接线测试；真板 `--gate4` 验证
>   `approved=true method=WS63 真板（SFC1）`。
> - **第 3 批 ✅**：新增 `screen-share` 演示样例（"把评审会纪要投屏到会议室大屏"），
>   控制台内真板端到端跑通：`闸4确认=1 闸4拒绝=0 method=WS63 真板（SFC1）`。
>   期间修了一个真实问题：闸4 路径拿到的串口传输由工厂持有，`ConsoleService.close()` 够不着，
>   进程会挂住并一直占 COM 口（表现为下一次 `Access denied`）；现在工厂提供 `close()`，
>   服务关闭时一并释放。
>
> **实现时确认的一个重要事实**：控制台把 `sendExternalEmail / deleteDoc / printDoc / deviceControl`
> 放进 `DEFERRED_ACTIONS`，走冻结操作闭环，**根本到不了闸4**；真正经过闸4 的是 `shareScreen`
> （员工策略 = confirm）等未转交的高危动作。所以闸4 接真板的价值主要在 shareScreen 与未来新增动作，
> 不是外发邮件——评审时不要把它和外发确认混为一谈。

## 1. 现状（必须先说清楚）

`runtime.cjs` 闸4 的判定链：

```js
if (!this._ablate('gate4') && (decision === 'confirm' || this._isHighRisk(action))) {
  const operation = { role, action, args, contentHash: digest(payload) };
  const challenge = this.confirmations.challenge(operation);          // 进程内 nonce
  const c = await requestHumanConfirm(step, { nearfieldOnline });     // ← 模拟
  const response = c.approved ? this.confirmations.simulateResponse(challenge) : null;
  if (!c.approved || !this.confirmations.consume(response, currentOperation)) → 拒绝
}
```

`requestHumanConfirm`（`src/guard.cjs`）的实现只有一句：

```js
if (nearfieldOnline) return { approved: true, method: '模拟确认（非真实 SLE 凭据…）' };
return { approved: false, method: '未检测到近场设备 → 超时拒绝' };
```

而 `nearfieldOnline` 来自 **控制台请求体**（`public/app.js` 的复选框，默认 `true`；
`console-service.cjs` 里 `nearfieldOnline: !!input.nearfieldOnline`）。

**结论：当前闸4 是客户端可控的布尔开关，不构成"人在设备前按了键"的证据。**
`ConfirmationService` 的 challenge/simulateResponse/consume 也只是进程内记账，防止的是
"同一 nonce 复用"，不是"未经真人确认"。

## 2. 目标与非目标

**目标**：高危动作执行前，必须拿到一条 SFC1 DECISION，满足：
1. 由配置的那台设备（`device_id`）签名；
2. 绑定该步骤将要执行的 payload 哈希（`operationHash = digest(payload)`）；
3. 在 TTL 内、nonce 未被消费（含跨重启，NV 窗口已实现）；
4. 取消/超时/错设备/重放/改帧一律拒绝执行。

**非目标**（写进材料时必须保留）：
- 不证明"按键的人是谁"，不证明设备与人的距离，不防中继；
- 不替代闸2/闸3/沙箱；
- 不改变非高危、非 confirm 的执行路径；
- 评测/消融（`disabledLayers: ['gate4']`）与 `eval/run.cjs` 默认行为不变。

## 3. 两条路线

| | A. 注入 `humanConfirm`（推荐先做） | B. step → 冻结操作 |
|---|---|---|
| 思路 | Runtime 接受一个 `humanConfirm(step, operation, challenge)`，控制台注入"板端确认"实现 | 把高危 step 映射成 `OperationStore` 里的冻结操作，整体复用控制台已有的 SFC1 闭环 |
| 改动面 | `runtime.cjs` 一个构造参数 + 一个调用点；新增一个板端实现模块 | runtime / console / store / fulfillment 全链路，执行语义变化 |
| 风险 | 低：默认实现不变，开关控制 | 高：运行时与操作库耦合，审计双写，暂停/恢复语义 |
| 复用 | 复用 SFC1 协议与串口 transport，不复用冻结操作 | 完全复用冻结闭环与审计链 |
| 结论 | **第一阶段做 A**；B 作为后续架构收敛选项 | 暂不做 |

## 4. 方案 A 细节

### 4.1 运行时接缝

```js
// runtime.cjs 构造
humanConfirm = null   // null = 保持现状（requestHumanConfirm 模拟）

// 闸4 调用点
const c = await this.perf.measureAsync('闸4 高危确认', () =>
  this.humanConfirm
    ? this.humanConfirm({ step, operation, challenge, ctx })
    : requestHumanConfirm(step, { nearfieldOnline: ctx.nearfieldOnline }),
);
```

返回值契约（与现状一致，便于最小改动）：

```js
{ approved: boolean, method: string, proof?: { confirmationId, deviceLabel, decidedAt } }
```

`proof` 只用于审计与展示，不参与 `confirmations.consume`——第一阶段保留
`ConfirmationService` 的 nonce 记账作为第二道防线（防同一次运行内重放）。

### 4.2 板端实现（新模块 `src/board-human-confirm.cjs`）

```js
createBoardHumanConfirm({ transportFactory, key, deviceId, ttlSec = 30, summaryOf })
  → async ({ operation }) => { approved, method, proof? }
```

流程：
1. 由 `operation.contentHash`（`digest(payload)`，32B）作为 `operationHash`；
2. 构造 SFC1 CHALLENGE（`taskId` 随机 8B、`nonce` 随机 16B、`action` 按映射表、`summary` ASCII）；
3. 通过 `nearfieldTransportFactory()` 取 transport，`send(frame)` 等 DECISION；
4. 用 `NearfieldConfirmer.acceptDecision` 验 MAC/绑定/nonce/TTL；
5. `decision=1` → `approved:true`；`decision=0` → `approved:false, method:'用户在板端取消'`；
   异常按 §6 映射为拒绝。

### 4.3 字段映射

| runtime action | SFC1 action | OLED summary（ASCII，≤96B） |
|---|---|---|
| `sendExternalEmail` | 1 SEND_EXT | `SEND EXT <domain>` |
| `deleteDoc` | 2 DELETE | `DELETE <docId>` |
| `printDoc` | 3 PRINT | `PRINT <printer>` |
| `deviceControl` | 4 DEVICE | `DEVICE <target>` |
| `uploadToCloud` | 4（暂借） | `UPLOAD <target>` |
| `shareScreen` | 4（暂借） | `SHARE <target>` |

> SFC1 v1 只有 4 个 action 码；新增 5/6 需要同时改 `ws63/protocol.c` 与 Node 侧并有单测，
> 第一阶段先借用 4，并在 OLED 摘要里写清楚真实动作，避免"码不对但界面看不出"。

**摘要必须 ASCII**：板端 OLED 字库不含中文，中文会显示 `?`（docs/57 §4）。

### 4.4 超时与并发

- TTL 默认 30s（与现有 `confirmations.challenge` 一致）；transport 超时 35s；
- 超时/无响应 → `approved:false`，闸4 拒绝，操作零执行；
- 单串口串行：两个并发命令会排队等同一块板；控制台需在返回里说明"等待板端确认"。

### 4.5 开关

- `SAFE_OFFICE_GATE4_NEARFIELD=1` 且配置了 `SAFE_OFFICE_NEARFIELD_PORT` 时，
  控制台构造 Runtime 注入板端实现；
- 否则保持现状（模拟），评测、E2E、无板演示不受影响。

## 5. 审计与可观测

闸4 确认/拒绝时写入（沿用现有 kind，新增字段）：

```json
{ "kind": "闸4确认", "n": 3, "action": "sendExternalEmail",
  "method": "WS63 真板（SFC1）", "operationHash": "...", "nonce": "...",
  "confirmationId": "ws63-...", "deviceLabel": "ws63-A", "decidedAt": 1730... }
```

拒绝时 `kind:"闸4拒绝"`，`method` 带上原因（`板端取消` / `超时` / `设备不符` / `传输错误`）。

## 6. 失败语义

| 情况 | 结果 | 说明 |
|---|---|---|
| 板端短按（decision=1） | 放行 | 记录 confirmationId |
| 板端长按（decision=0） | 拒绝 | `method:'用户在板端取消'`，操作零执行 |
| transport 超时 | 拒绝 | `method:'板端无响应'` |
| 串口打不开 | 拒绝 | `method:'确认端不可用:<err>'`；**不得回退到模拟** |
| 设备 ID 不符 / MAC / 重放 | 拒绝 | 由 `acceptDecision` 抛出的 code 映射到 method |
| 挑战过期 | 拒绝 | 同上 |

**关键约束：任何失败都不能 fallback 到 `nearfieldOnline` 模拟放行。**

## 7. 安全边界（得到什么、没得到什么）

**得到**：
- 高危动作的确认绑定了具体 payload 哈希与设备；
- 重启后旧 nonce 仍被拒（M1 已实现）；
- 客户端无法用布尔开关绕过（开关只影响是否要求真板，不能伪造 DECISION）。

**没得到**：
- 按键者身份、设备与人距离、防中继；
- PSK 仍编译在固件镜像里（一机一钥/HUKS 未做）；
- NV 被物理擦除时窗口回到空（fail-open，可被物理接触绕过）；
- 传输层是 USB 串口，不是近场无线。

## 8. 实施步骤（建议分三批）

1. **接缝 + 单测**：`runtime.cjs` 加 `humanConfirm`；用假函数测放行/拒绝/异常；默认路径不变。
2. **板端实现 + 控制台开关**：新增 `src/board-human-confirm.cjs`；控制台在开关打开时注入；
   加服务层测试（假 transport）。
3. **真板验收 + 文档**：真板跑 `sendExternalEmail` 高危步骤（短按通过 / 长按拒绝 / 拔线拒绝），
   更新 docs/11、docs/57，补真机记录。

## 9. 测试计划

- 单测：`humanConfirm` 放行/拒绝/抛错 → 闸4 三条分支；`disabledLayers:['gate4']` 仍跳过。
- 服务层：假 transport 返回 DECISION → 命令执行；返回取消/超时 → 拒绝且零副作用。
- 真板：短按、长按、断电、错设备（`--device` 不符）。
- 回归：`npm test` 486+；E2E 11/11（虚拟模式）；`eval/run.cjs` 结果不变（默认开关关闭）。
