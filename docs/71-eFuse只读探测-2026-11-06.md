## 4. 结论

1. **地址映射正确**：`uapi_efuse_user_read_buffer(0, 16B)` 与
   `uapi_efuse_read_buffer(buf, 222, 16B)` 返回完全一致（`match=yes`），
   证实客户预留区确为**第 222 字节起 16B**。
2. **当前为空**：16 字节全 `0x00`（`ones=0`），符合 OTP 未烧写的预期。
3. **可读性通过**：两条读路径 `rc=0`，量产芯片上该区可正常读取。
4. **可写性仍未验证**：本轮没有调用任何写接口；OTP 只能 0→1，且当前只剩一块可用板，
   是否写 KEK 需单独拍板（见 docs/60 §8）。

## 5. 边界（不夸大）

- 该区**无读保护**：能执行代码仍可读出内容；收益仅限「拆外部 Flash dump 拿不到密钥」，
  不是「物理不可提取」。
- 16B 预留区**小于**现有 32B SFC1 密钥，不能直接搬运；若写入，只能走
  **KEK 方案**（eFuse 存 16B KEK，NV 存 `AES-GCM(KEK, 32B key)`）。
- 本轮只证明「读得到、当前为空」，**不证明「写得进、写后可用」**。

## 6. 复现

```bash
cd prototype
npm run efuse:probe -- --port COM11
```

退出码：0 = 收到完整探测块；3 = 串口 0 字节；4 = 有数据但无完整块。
