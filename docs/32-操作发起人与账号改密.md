# 操作发起人、四眼原则与账号改密（v0.31）

> 2026-10-31 恢复开发后的第一轮软件收尾。目标是把「谁发起的操作」变成冻结记录的一部分，
> 让「自己发起、自己批准」在服务端可拦；同时补上账号改密与 E2E 覆盖。
> 本轮**没有**做租户隔离、2FA、ClamAV 安装。

## 1. 操作发起人（createdBy）

**改了什么**

- `operation.cjs`：`sealOperation` 接收 `createdBy`（登录用户名，截断 64 字符），并写入
  `operationHash` 的规范化内容。空值不写入规范化 JSON → **升级前冻结的旧记录哈希不变**，
  `verifyOperation` 仍通过。
- `store.cjs`：`operations` 表新增 `created_by`；启动时用 `PRAGMA table_info` 检查，旧库自动
  `ALTER TABLE ADD COLUMN`。`insertOperation` 写入，`getOperation/listOperations` 读回。
- `console-service.cjs`：`_executeCommand` 把 `operator` 传给 `_freezeDeferred`，冻结时写入
  `createdBy`；草稿重新冻结保留原发起人；`_operationView` 暴露 `createdBy`。
- 前端：审批卡片与操作详情显示「发起人」。

**为什么放进哈希**

只存在 `operation_meta` 里的话，能改 SQLite 的人也能改发起人。放进 `operationHash` 后，
改 `createdBy` 会让 `verifyOperation` 失败，确认/执行都会被拒。

**兼容性**

- 旧记录 `created_by` 为 `''`；规范化 JSON 省略该字段，哈希与升级前一致。
- 新记录哈希包含 `createdBy`，重放旧哈希不会误通过。

## 2. 四眼原则（发起人不能批准自己的操作）

**服务端拦截点**

- `ConsoleService._assertNotSelfApproval(operation, actor)`：当 `actor === operation.createdBy`
  且决定是「批准」时，抛 `FORBIDDEN`，并写审计 `四眼原则拒绝`。
- 只在 `decideChallenge(..., { actor })` 的虚拟设备批准路径生效；被拒时 **nonce 不消费**，
  操作保持 `frozen`，换一位审批人仍可继续。
- 拒绝（cancel/reject）不受限：撤回自己的请求不是提权。
- `server.cjs` 把登录用户名从会话传给 `decideChallenge` / `rejectOperation` /
  `beginChallenge`。

**边界（重要）**

- 手机确认端 / 真实 WS63 没有「登录用户」身份，服务端无法判断按键的人是谁；这条路径靠
  「确认发生在另一台设备上」的物理边界，**不是**密码学身份绑定。
- 自动模式（`auto-safe` / `auto-full`）与策略自动确认（`policy-auto`）属于策略放行，
  不经过四眼检查；演示模式本身已在界面明确警告。
- 当前内置角色下，员工能发起业务动作但无权虚拟批准，管理员能批准但不做业务动作；
  四眼检查是对未来角色/自定义工具与更细权限的兜底，不是现有唯一防线。

## 3. 账号改密

**服务端**

- `AuthService.changePassword(username, oldPassword, newPassword, { keepToken })`：
  校验原密码 → 拒重复/过短 → 重新 scrypt（新 salt）→ **先写 `users.json` 再改内存**
  （写盘失败不会出现「内存已改、磁盘没改」）→ 注销该用户其他会话，保留当前 token。
- `POST /api/change-password`：需登录；原密码错误 401 `INVALID_CREDENTIALS`，参数问题
  400；5 次/分钟/IP 限流。无用户表时 409。
- 前端：顶栏「改密」弹窗（原生 `<dialog>`），失败就地显示，不触发 API 的 401 跳登录。

**未做**

- 2FA、会话持久化（重启仍要重新登录）、管理员重置他人密码、密码强度策略（目前只要求 ≥8 位）。

## 4. E2E 扩展

`e2e/ui.e2e.cjs` 从 1 条扩到 2 条：

1. 登录 → 工作台样例 → 审批页 → （管理员）上传 `.txt` → 改密 → 退出 → 新密码重登。
2. 员工发起外发 → 发起挑战 → 手机确认端独立上下文配对 → 端上签名批准 → 控制台显示「已执行」。

## 6. 明确没做的

- **租户隔离**：仍共享同一工作区；本轮只记录 owner，不按用户隔离数据。
- **ClamAV**：本机未安装；`off/auto/required` 逻辑与 fail-closed 已有测试，但未做真实病毒库扫描。
- **手机端四眼**：无用户身份，见 §2 边界。
